# 如何判断机场晚高峰是否稳定？20:00–23:30 标准化验证与路由跟踪指南

<div class="answer-first-box">

很多用户选机场时都有过类似落差：午休或凌晨看评测图时，香港节点延迟 `22ms`、速度 `500Mbps`，一到晚上九点自己在家打开却连 AI 网页都要转圈五六秒。之所以出现这种“白天飞快、晚上卡死”的反差，核心原因在于国内三网宽带（电信、联通、移动）与中转机房的并发负载高度集中在 **20:00–23:30** 这一窗口。白天宽裕的入口带宽掩盖了超售和跨网绕行，只有晚高峰才能把链路的真实承压能力照出来。

本指南承接[稳定机场与抗衰减规范](/airport/stable/)，聚焦普通用户自己在家就能跑通的 **四步晚高峰标准化自测流程**，同时讲清如何正确看待库内的历史数据边界。

## 一、适用系统与历史数据局限说明

### 1. 适用系统与本地工具

本文提供的命令以最常见的 **Windows 10 / 11 PowerShell** 为主（内置 `curl.exe`，无需额外装库），同时给出 macOS / Linux 对应的 `curl` 与 `NextTrace` / `MTR` 替代命令。测试对象为支持导入第三方通用订阅（[Clash Verge Rev](/clients/clash-verge-rev/)、[FlClash](/clients/flclash/)、[v2rayN](/clients/v2rayn/)）的机场节点。

### 2. 为什么必须自己测？看清三类历史数据的客观局限

在参考本站品牌档案或网上测评图之前，必须先认清历史记录为什么不能替代你家里宽带的晚高峰自测：

1. **`2026-10-19 非晚高峰历史汇总` 的局限**：
   在本站整理的 31 家机场数据库中，包括[光速云](/brands/guangsuyun/)、[一翻云](/brands/yifan/) 等在内的 15 家品牌均附有一组标记为 `2026-10-19 非晚高峰` 的 5 地区测速记录（香港集中在 `21–27ms / 477–548Mbps`、美国集中在 `134–180ms / 14–30Mbps`）。但根据数据审计结论，这批数据**明确注记为非晚高峰**，且未附测速软件版本、并发线程数、具体节点编号及本地宽带运营商信息，**绝对不能用来证明某家机场晚上八点到十一点半不会丢包限速**。
2. **`guangsuyun` 2026-08-19 归档图揭示的跨网反差**：
   在[光速云](/brands/guangsuyun/) 2026-08-19 留存的 5 张 MiaoKo 归档截图中，同一批 62 个 Shadowsocks 节点在 `SC-2.3.1 长沙电信@2Gbps` 环境下，香港专线节点测得 `TLS RTT 20–31ms`、体感 `HTTPS 延迟 81–111ms`（`广西移动@2Gbps` 下香港专线 `TLS RTT` 同样在 `22–32ms`）；然而切换到 `河北联通@2Gbps` 后，同一批香港节点的 `TLS RTT` 跳升至 `53–100ms`，多个香港节点的 **`HTTPS 延迟` 更直接飙升到 `1200ms–1372ms`**！这证明哪怕在同一天，不同省份、不同运营商接入同一家机场的体感也会出现天壤之别。
3. **`lingdong` 2026-07 归档的特殊测试环境限制**：
   [灵动云（lingdong）](/brands/lingdong/) 在 `2026-07-20 / 2026-07-21` 留有一份罕见的真实测试摘要，录得全节点 `20–80 MB/s`（约合 `160–640 Mbps`）。但它是在 **珠海联通 9Gbps** 的高带宽机房环境下跑出的 60 节点样本，且档案如实保留了 **HTTPS 延迟偏高、美国 01 整节点失败、TikTok 多节点失败及新台 YouTube 送中** 等缺点。既不能把 9Gbps 联通专机环境直接套用到你家的 300M 电信或移动宽带上，也不能忽视 2026 年 7 月至今节点可能发生的变化。

## 二、准备事项：用真实月付控制试错成本

在晚上 20:00 开始测试之前，做好以下三项准备，才能保证测试数字干净、可复现、且买错不肉痛：

1. **坚持从真实月付入门档起步（拒绝首单直接年付）**：
   很多品牌首页标“¥5.6/月”或“¥8.25/月”其实是年付一次性付清的折算价，且绝大多数机场声明虚拟商品不支持退款。测试晚高峰稳定性时，务必选择支持单月购买的常规月付入门档（例如 ¥18–¥25 档位），把最大试错成本锁定在一顿饭钱内。像[一翻云](/brands/yifan/)在资料中同时提供 `Hysteria 2`、`VLESS-Reality` 与 `Shadowsocks` 三种协议，如果遇到某省晚高峰针对 UDP 实施 QoS 限速，还能在同套餐内切换 TCP/Reality 协议做对照测试。
2. **清理本地测速干扰源**：
   测试前关闭电脑和同局域网其他设备上的网盘同步、Steam/系统更新、BT 下载和 4K 视频缓存；笔记本电脑尽量插网线，或者靠近 5GHz Wi-Fi 路由器，排除室内无线信号衰减造成的虚假抖动。
3. **确认本地代理监听端口并准备好 NextTrace**：
   - 在 [Clash Verge Rev](/clients/clash-verge-rev/) 中确认混合端口（默认通常为 `7897`；若使用 [v2rayN](/clients/v2rayn/) 默认 HTTP 端口通常为 `10809`）。
   - 前往 NextTrace 官方开源仓库下载对应系统版本的可执行文件（Windows 下为 `nexttrace.exe`），放入终端可调用路径中；macOS / Linux 用户也可使用系统包管理器安装 `mtr` 或 `nexttrace`。

## 三、实际操作：20:00–23:30 四步标准化自测流程

请分别在**白天非高峰时段（如 14:00–16:00）**跑一次作为基准线，然后在**晚高峰核心区间（建议 20:30–22:30）**严格按以下四步执行同一组命令。

### 第一步：用 `curl.exe -w` 连续采样 `TLSconnect` 与 `TTFB`

客户端软件自带的“测延迟”往往只发一次轻量探测，容易掩盖晚高峰的脉冲式丢包。我们需要通过本地代理端口向海外固定探测端点（例如 Cloudflare 204）连续发起 15 次完整 HTTPS 请求，同时抓取三项指标（详见[延迟与抖动原理](/routes/latency/)）：
- `time_connect`：本地到境内入口机的 TCP 握手耗时；
- `time_appconnect`：穿透整个代理隧道与海外目标完成 TLS 握手的耗时（`TLSconnect`）；
- `time_starttransfer`：从发出请求到收到第一个响应字节的首字节时间（`TTFB`）。

在 Windows PowerShell 中执行以下命令（假设本地代理端口为 `7897`，若不同请替换数字）：

```powershell
# 第一步：连续 15 次采集 TCP、TLSconnect 与 TTFB（单位：秒）
$proxy = "http://127.0.0.1:7897"
$url = "https://cp.cloudflare.com/generate_204"
$fails = 0

1..15 | ForEach-Object {
  $res = curl.exe -x $proxy --connect-timeout 5 -m 8 -s -o NUL `
    -w "%{http_code}|%{time_connect}|%{time_appconnect}|%{time_starttransfer}" $url
  $parts = $res -split '\|'
  if ($parts[0] -ne "204") {
    $fails++
    Write-Host ("第 {0:D2} 次 | 失败或超时 (HTTP={1})" -f $_, $parts[0]) -ForegroundColor Red
  } else {
    $tcp = [math]::Round([double]$parts[1] * 1000, 1)
    $tls = [math]::Round([double]$parts[2] * 1000, 1)
    $ttfb = [math]::Round([double]$parts[3] * 1000, 1)
    Write-Host ("第 {0:D2} 次 | HTTP:204 | TCP:{1}ms | TLSconnect:{2}ms | TTFB:{3}ms" -f $_, $tcp, $tls, $ttfb)
  }
  Start-Sleep -Seconds 1
}
Write-Host ("=== 采样汇总：15 次中失败 {0} 次 ===" -f $fails) -ForegroundColor Cyan
```

**判读要点**：如果 `TCP` 只有 `25ms` 但 `TLSconnect` 跳到 `900ms` 以上或出现红字超时，说明第一跳入口虽近，但**跨境中转段或入口出口在晚高峰发生了严重排队与丢包**——这正是北方联通在 `2026-08-19` 归档图中出现 `1200ms+` HTTPS 延迟的典型表现。

### 第二步：单线程 `25MB / 50MB` 实测，戳破多线程 Speedtest 幻觉

很多人晚高峰习惯打开 Speedtest 网页版测一下跑分，看到显示 `200Mbps` 就以为很稳，结果看 YouTube 4K 照样缓冲。这是因为 Speedtest 默认开启 **8 到 16 条并发 TCP 连接**。即便机场后台对每条连接做了 `10Mbps` 限速，或者线路有 `2%` 随机丢包导致单连接无法爬高，多线程并发依然能把总速度堆到看起来很漂亮；但你日常刷网页、拉取 GitHub release 包、接收 ChatGPT 流式响应和播放视频，底层依赖的往往只有 **1 到 2 条单连接**。

因此，晚高峰必须使用 `curl.exe` 强制单线程拉取固定大小的测试文件（先测 `25MB`，若稳再测 `50MB`），观察真实单线程平均吞吐：

```powershell
# 第二步：单线程下载 25MB 样本文件（26214400 字节），结果直接丢弃不占硬盘
curl.exe -x http://127.0.0.1:7897 -s -o NUL `
  -w "状态码:%{http_code} | 总耗时:%{time_total}s | 单线程均速:%{speed_download} B/s`n" `
  "https://speed.cloudflare.com/__down?bytes=26214400"

# 若 25MB 顺畅，进一步加测 50MB 持续拉流抗衰减（52428800 字节），观察是否半途断流
curl.exe -x http://127.0.0.1:7897 -s -o NUL `
  -w "状态码:%{http_code} | 总耗时:%{time_total}s | 单线程均速:%{speed_download} B/s`n" `
  "https://speed.cloudflare.com/__down?bytes=52428800"
```

**单位换算提醒**：`curl.exe` 输出的 `%{speed_download}` 单位是字节每秒（`B/s`）。把它除以 `1048576` 即得到 **`MB/s`**，再乘以 `8` 即得到 **`Mbps`**。例如输出 `8388608 B/s`，换算后就是 **`8.0 MB/s`**（约 **`64 Mbps`**）。如果下午单线程能跑到 `30 MB/s`，晚上 21:00 跌到 `0.8 MB/s`（衰减率超过 `95%`），即便多线程测速能跑 `100Mbps`，这条节点在晚高峰也不及格。

### 第三步：用 `NextTrace` / `MTR` 追踪入口 IP 跳点与丢包

当你在前两步发现晚高峰延迟暴涨或丢包时，怎么判断问题是出在“你家宽带连国内入口的第一跳”，还是出在“机场入口之后”？这就需要在**彻底关闭代理客户端（关闭系统代理和 TUN）**的前提下，对节点配置文件里的服务器地址运行 `NextTrace` 或 `MTR`（记住：切勿使用尖括号直接当参数，请把下面占位符替换成你订阅里的真实域名或 IP）：

1. 先从订阅 YAML 或节点详情里抄出该节点的服务器域名（例如 `node-hk01.example.com`），用 `nslookup` 查出入口 IP。
2. 在 Windows PowerShell 中用 `NextTrace` 追踪该入口 IP（TCP 模式更贴近真实代理端口连通性，例如将端口换为节点实际端口 `443`）：

```powershell
# 先解析节点入口域名获取真实入口 IP
nslookup node-hk01.example.com

# 关闭代理后，使用 NextTrace 对入口 IP 运行 TCP 路由追踪（把 203.0.113.10 替换为实际入口 IP）
nexttrace -T -p 443 203.0.113.10
```

若在 macOS / Linux 下习惯看连续跳点丢包率，可使用 `mtr` 连续发送 30 个探测包：

```bash
# 对境内入口 IP 连续发送 30 次 TCP 探测并汇总各跳丢包率（把 203.0.113.10 替换为实际入口 IP）
sudo mtr -T -P 443 -c 30 -r 203.0.113.10
```

**路由跟踪判读原则**：
- **情形 A（国内入口前就丢包或跨省大绕行）**：如果你家是北方联通，而入口 IP 是广州电信单线机房，且在到达入口前的省际骨干网跳点就已经出现 `5%–15%` 丢包或延迟暴涨到 `120ms+`，说明这家机场的国内前置没有做好三线 BGP 接入，问题出在“第一跳跨网拥堵”。
- **情形 B（入口 IP 全程零丢包且延迟 20ms，但第一步的 `TLSconnect` 却超过 1000ms）**：说明你家到国内入口很顺畅，真正卡死的是**入口机器本身 CPU/端口满载超售，或者入口机后面的跨境段/海外落地段在晚高峰严重拥塞**。

### 第四步：连续 3 天晚高峰对比日志模板

单晚测一次可能正好撞上某个机房临时割接或线路维护，下结论至少需要连续观察 **3 天（建议包含 2 个工作日 + 1 个周末晚间）**。建议用如下表格记录你的实测日志：

## 四、成功验证：合格与淘汰的量化判定线

把 3 天的记录填完后，对照以下工程门槛直接做留存或止损决策：

1. **优秀稳态（可长期续费）**：3 晚峰值失败率均为 `0%`；亚太节点（港/日/新/台）`TTFB` 稳定在 `250ms` 以内；`50MB` 单线程持续下载保持在 **`10 MB/s`（80 Mbps）以上**且较白天衰减 `< 30%`。
2. **合格可用（满足日常办公与 4K）**：偶发抖动但失败率 `< 5%`；`TTFB` 处于 `150–350ms`；单线程均速稳定在 **`5–10 MB/s`（40–80 Mbps）** 且下载过程中没有归零停顿。
3. **不达标（月底到期不续或仅留作备用）**：连续两晚出现请求超时失败；`TTFB` 动辄突破 `800ms–1200ms`；`50MB` 单线程掉到 `2 MB/s` 以下且衰减超过 `80%`。如果该机场同时提供 `Hysteria 2` 与 `VLESS` 多协议，可先切换协议再复测一晚，仍不行则直接果断弃用。

## 五、常见错误与排查

1. **错误一：开着系统代理或 TUN 模式去跑 `NextTrace` / `MTR`**
   - **现象**：追踪出来的第一跳直接是本地虚拟网卡 `198.18.0.1`，后面全部星号或假回包。
   - **修正**：执行 `NextTrace` / `MTR` 检查物理链路前，**必须先彻底退出或关闭代理软件的代理与 TUN 开关**，并且追踪的是“节点的境内入口域名/IP”，而不是 Google 或 Cloudflare 的域名。
2. **错误二：把 `speed_download` 的 `B/s` 直接当成 `Mbps`**
   - **现象**：看到终端显示 `6,291,456`，以为速度只有 `6 Mbps`，误判节点极慢。
   - **修正**：记住 `1 MB/s = 1,048,576 B/s = 8 Mbps`。`6,291,456 B/s` 实际上等于 `6.0 MB/s` 即 **`48 Mbps`**，已经足够流畅播放 4K 视频。
3. **错误三：只跑 1 次 `curl` 或只看客户端内绿字就定结论**
   - **现象**：单次恰好避开丢包瞬间，或者客户端自带延迟只测到境内入口的 TCP 握手（`25ms`），实际打开海外 AI 网页依然超时。
   - **修正**：遇到类似“节点全绿但网页打不开”的情况，先排查[节点超时与系统时间问题](/troubleshooting/timeout/)，并以至少连续 15 次 `TLSconnect` 和 `TTFB` 采样作为客观依据。
4. **错误四：拿广州电信朋友的晚高峰体验，去替北京联通自己做决定**
   - **现象**：看到群里华南网友发图说飞快，自己一买回去晚上掉包卡顿。
   - **修正**：参考上文[光速云](/brands/guangsuyun/) `2026-08-19` 跨网反差实例，不同省份、不同运营商的路由差异极其显著，**永远只采信你自己在当前宽带上跑出的 3 天晚高峰日志**。

## 常见问题（FAQ）

### 为什么数据库里的 2026-10-19 测速汇总表不能证明机场晚高峰稳定？

因为本站库内 15 家品牌收录的 2026-10-19 测试表格在原始资料中明确注明为“非晚高峰”历史汇总记录，且缺少测速工具名称、并发线程数、节点编号与测试地宽带运营商信息（港台新日美高度集中）。非晚高峰网络负载远低于 20:00 至 23:30 的三网并发峰值，完全无法反映晚间超售排队与跨网 QoS 拥塞。

### 晚高峰为什么要用 curl 单线程下载 25MB/50MB 文件，而不能只看 Speedtest 多线程跑分？

网页版 Speedtest 默认会同时建立 8 至 16 条并发连接，即便机场中转端在晚高峰对单条连接限速或存在轻微丢包，多线程并发也能拼出上百 Mbps 的虚高总带宽。但你实际打开网页、加载 GitHub、观看 4K 视频流或接收 AI 流式输出时，主要依赖单条或极少数连接，只有单线程 25MB 至 50MB 持续拉流速度才接近真实体感。

### 为什么同一家机场，南方电信测出来延迟很低，北方联通晚上却卡顿明显？

因为代理链路由“本地宽带到境内入口”和“境内入口到海外落地”两段构成。以本站归档的光速云 2026-08-19 MiaoKo 测试图为例，同一批 62 个 Shadowsocks 节点在长沙电信与广西移动环境下香港专线 HTTPS 延迟约为 80ms 至 110ms，但在河北联通网络下多个香港节点 HTTPS 延迟却飙升至 1200ms 以上，跨省跨网路由差异极其显著。

### 灵动云 2026-07 珠海联通 9Gbps 测试显示 20–80 MB/s，是不是代表普通家庭宽带晚上也能跑这么快？

不能直接外推。一方面 20 至 80 MB/s（换算为 160 至 640 Mbps）是在珠海联通 9Gbps 大带宽专机环境下跑出的历史归档数据，远高于普通家用百兆或千兆宽带且属不同运营商路径；另一方面该份归档自己也记录了 HTTPS 延迟偏高、美国 01 整节点失败与部分流媒体异常，购买前仍须在你自己的家庭宽带上实测。

### 用 NextTrace 或 MTR 做路由跟踪时，应该追节点域名还是落地 IP？

在本地关闭代理的状态下，应当用 NextTrace 或 MTR 追踪订阅节点里的“连接服务器域名或 IP”（也就是境内前置入口地址）。这样可以检查你的本地宽带到入口机房之间是否发生跨网绕路或中间跳丢包；如果你开着代理去追海外网站，数据包走的是加密隧道，本地路由跟踪看不到真实跨境路径。

### 连续 3 天晚高峰测试下来，什么指标才算真正通过了稳定性验收？

如果在连续 3 个晚间（包含工作日与周末）的 20:00 至 23:30 时段内，主力节点连续 20 次 HTTPS 请求的失败率为 0%、TTFB 波动平稳且香港/日新节点保持在 300ms 以内、单线程 50MB 持续下载不出现归零断流且稳定在 5 MB/s（40 Mbps）以上，就说明该节点对你的本地宽带具备良好的晚高峰可用性。
