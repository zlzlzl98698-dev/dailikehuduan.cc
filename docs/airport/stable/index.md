## 一、定义 20:00–23:30 晚高峰窗口：三网拥塞特征与历史数据边界

要建立科学的“稳定节点”评估体系，必须先划清测试窗口与历史参考数据的使用边界，避免拿过时或非高峰跑分做错误决策。

### 1. 为什么是 20:00–23:30？三大拥堵叠加点
在这个长达 3.5 小时的晚高峰窗口内，跨境代理链路同时承受三层压力：
1. **第一层（本地最后一公里与城域网汇聚拥堵）**：居民区光猫上联 OLT 端口与城域网 BRAS 在晚 20:30 后达到峰值，尤其是部分移动宽带和校园网在此时段会自动收紧国际方向或陌生高频端口的并发策略。
2. **第二层（国内入口机房带宽与跨网互联拥堵）**：机场租用的广东、上海或北京入口转发服务器（例如多用户共用一台 1Gbps 或 2.5Gbps 带宽端口的母鸡），晚高峰在线并发人数通常是白天的 4–6 倍。如果商家按“1:10”以上比例超售带宽，入口网卡队列就会迅速堆积，表现为延迟陡增和间歇性断流。
3. **第三层（海外落地出口与目标平台限流）**：晚上 21:00–23:00 恰好重叠欧美工作时段或亚洲用户娱乐高峰，落地 VPS 机房的共享带宽及上游 CDN 节点同样处于高负荷状态。

## 二、核心技术指标拆解：TCP/TLS RTT vs ICMP 与单线程吞吐衰减率

为什么很多新手看着客户端里 `35ms` 的延迟，打开网页却要等四五秒？答案在于测速机制与实际应用流量模型的根本错位。

### 1. ICMP Ping、TCP RTT、TLS RTT 与 HTTP TTFB 的四层差异
在网络排障与机场测评中，四个延迟指标的含金量逐级递升：

1. **ICMP Ping（最低参考价值）**：传统命令行 `ping` 发送的是 ICMP Echo 请求。不仅无法穿透代理隧道测试海外落地真实路径（大多数代理客户端根本不转发 ICMP 到远端节点，或者仅由本地 TUN 虚拟网卡伪造回包），而且许多专线中转机房会对 ICMP 报文降级限速甚至直接禁 Ping。
2. **TCP 握手 RTT（`time_connect`）**：测量本地客户端到代理节点建立 TCP 三次握手的时间。如果机场使用的是“国内中转入口”，你测到的 TCP RTT 往往只是你家宽带到广州或上海入口机房的物理延迟（例如 `25ms`），**完全不包含后半段跨海专线和海外落地的真实延迟**！
3. **TLS 握手 RTT（`time_appconnect`）**：当你通过代理访问一个 HTTPS 网站（如 `cp.cloudflare.com` 或 `openai.com`）时，TLS 握手必须穿透整个代理链路直达海外目标服务器完成密钥协商。如果机场的国内入口到海外落地段存在丢包或高负载排队，TLS 握手耗时就会从正常的 `0.08s` 暴涨到 `1.5s` 甚至超时。
4. **HTTP 首字节时间 TTFB（`time_starttransfer`）**：从发出 HTTP 请求到收到目标服务器第一个响应字节的总耗时。它完整串联了 **本地代理处理 + 入口传输 + 跨海专线 + 落地解析 DNS + 目标站回包** 的全链路质量。关于更多底层延迟原理，可配合查阅 [低延迟、丢包与抖动解析](/routes/latency/)。

### 2. 单线程吞吐衰减率（衡量超售与限速的黄金公式）
为什么不能只用 Speedtest 网页版跑多线程测速？因为 Speedtest 默认会同时开启 8 到 16 条并发 TCP 连接抢占带宽。即便机场服务端对每条连接做了 `10 Mbps` 限速，或者链路存在 1% 丢包导致单连接窗口难以爬升，多线程依然能凑出 `120 Mbps` 的虚高总分；但当你实际打开 YouTube 播放 4K 视频、从 GitHub 下载 release 包、或用 `curl` 拉取大模型数据时，系统建立的只有 **1 到 2 条单连接**。

因此，真正衡量一条节点晚高峰是否稳定的核心指标，是**单线程吞吐衰减率**：

> **单线程吞吐衰减率** = `(非晚高峰单线程速率 − 20:00–23:30 晚高峰单线程速率) ÷ 非晚高峰单线程速率 × 100%`

在实际宽带环境下，我们的工程判读基准线如下（注意区分单位：`1 MB/s = 8 Mbps`）：
- **优秀（旗舰稳态级）**：晚高峰单线程衰减率 `< 20%`，亚太节点（港/日/新/台）晚高峰单线程实测稳定在 **10–30 MB/s（80–240 Mbps）** 以上，拖动 4K 60fps 视频进度条在 1 秒内起播。
- **合格（日常可用级）**：晚高峰衰减率在 `20%–45%`，但绝对速率依然稳定维持在 **5–10 MB/s（40–80 Mbps）**，且传输曲线平稳、不出现周期性归零卡顿。这个速率足以保障 4K 视频不缓冲与 AI 流式输出流畅。
- **不合格（严重超售或 QoS 拥堵）**：白天单线程 `40 MB/s`，一到晚上 21:00 暴跌至 `1.2 MB/s` 以下（衰减率 `> 90%`），或者下载过程中出现数秒停顿归零。此时无论客户端延迟表显示多少毫秒，该节点在晚高峰均属于不可用状态。

## 三、晚高峰实测与连续丢包/抖动监控脚本（即拿即用）

买完月付测试套餐并导入 [Clash Verge Rev](/clients/clash-verge-rev/)、[FlClash](/clients/flclash/) 或 [v2rayN](/clients/v2rayn/) 后，请于 **20:30–22:30** 之间关闭本地下载工具，在终端直接运行以下两组标准化测试脚本（以下默认代理本地 HTTP 端口为 `7897`，若使用 v2rayN 的 `10809` 或其他端口请自行替换数字）。

### 脚本 1：连续 30 次 TCP/TLS/TTFB 采样与抖动/失败率统计（Bash / macOS / Linux / WSL）
仅跑 1 次请求无法捕捉抖动和丢包。下面这段单行或小脚本会每间隔 1 秒连续发起 30 次 HTTPS 探测，直观暴露晚高峰是否存在脉冲式丢包与极端长尾延迟（P95 飙高）：

```bash
# 连续 30 次测试通过代理访问 Cloudflare 204 端点的 TLS 耗时、TTFB 与失败次数
PROXY="http://127.0.0.1:7897"
URL="https://cp.cloudflare.com/generate_204"
fail=0

for i in $(seq 1 30); do
  res=$(curl -x "$PROXY" --connect-timeout 5 -m 8 -s -o /dev/null \
    -w "%{http_code} %{time_connect} %{time_appconnect} %{time_starttransfer}" "$URL")
  code=$(echo "$res" | awk '{print $1}')
  if [ "$code" != "204" ]; then
    fail=$((fail+1))
    echo "Run $i | FAILED (code=$code)"
  else
    echo "Run $i | HTTP:$code | TCP:$(echo "$res" | awk '{print $2}')s | TLS:$(echo "$res" | awk '{print $3}')s | TTFB:$(echo "$res" | awk '{print $4}')s"
  fi
  sleep 1
done
echo "=== 采样总结: 总计 30 次, 失败/超时 $fail 次 (失败率 $((fail*100/30))%) ==="
```

### 脚本 2：Windows PowerShell 连续延迟抖动 + 单线程吞吐双测脚本
针对绝大多数 Windows 桌面端用户，直接打开 PowerShell（无需安装第三方工具）运行以下两段命令即可获得真实数据：

```powershell
# 1) 连续 20 次晚高峰 HTTP TTFB 与丢包/超时采样（假设端口 7897）
$proxy = "http://127.0.0.1:7897"
$fails = 0
$ttfbList = @()

1..20 | ForEach-Object {
  $out = curl.exe -x $proxy --connect-timeout 5 -m 8 -s -o NUL `
    -w "%{http_code}|%{time_connect}|%{time_appconnect}|%{time_starttransfer}" `
    "https://cp.cloudflare.com/generate_204"
  $parts = $out -split '\|'
  if ($parts[0] -eq "204") {
    $ttfb = [double]$parts[3]
    $ttfbList += $ttfb
    Write-Host ("Run {0:D2} | TCP:{1}s | TLS:{2}s | TTFB:{3}s" -f $_, $parts[1], $parts[2], $parts[3])
  } else {
    $fails++
    Write-Host ("Run {0:D2} | TIMEOUT / ERROR (code={1})" -f $_, $parts[0]) -ForegroundColor Red
  }
  Start-Sleep -Seconds 1
}

if ($ttfbList.Count -gt 0) {
  $sorted = $ttfbList | Sort-Object
  $avg = ($ttfbList | Measure-Object -Average).Average
  $p95Index = [Math]::Floor($sorted.Count * 0.95)
  if ($p95Index -ge $sorted.Count) { $p95Index = $sorted.Count - 1 }
  Write-Host ("`n统计结果 -> 成功:{0}/20 | 失败率:{1}% | 平均TTFB:{2:N3}s | P95长尾:{3:N3}s" -f $ttfbList.Count, ($fails*5), $avg, $sorted[$p95Index])
}

# 2) 单线程 50MB 持续吞吐测试（注意：每次运行消耗约 50MB 套餐流量）
curl.exe -x $proxy --connect-timeout 8 -m 45 -o NUL `
  -w "`n单线程平均速度: %{speed_download} B/s | 总耗时: %{time_total}s | 状态码: %{http_code}`n" `
  "https://speed.cloudflare.com/__down?bytes=52428800"
```

| **亚太节点 TTFB 均值** | **0.08s – 0.25s** | 0.26s – 0.55s | **大于 0.60s** |
| **TTFB 抖动幅度（P95 − 均值）** | **小于 0.12s**（曲线极平） | 0.12s – 0.35s | **大于 0.40s**（打开网页时快时慢） |
| **单线程持续下载速率** | **≥ 8 MB/s（64 Mbps）** | 4 – 7.9 MB/s（32–63 Mbps） | **小于 3 MB/s（24 Mbps）**（4K 无法稳播） |

> **排障提示**：如果在运行脚本时所有节点无一例外报 `TIMEOUT` 或 TLS 失败，先不要直接认定机场崩溃。先排查系统本地时间是否偏差导致 TLS 校验失败（详见 [系统时间 TLS 修复](/guides/system-time-tls-fix/)），以及是否开启了冲突的系统代理端口（详见 [节点全部超时排查](/troubleshooting/timeout/) 与 [断线排查手册](/troubleshooting/disconnected/)）。

## 四、IEPL / IPLC / BGP 中转与现代协议的稳定性条件

不少商家在宣传页上只要写上 `IEPL` 或 `IPLC`，用户就默认它“绝对稳”。从传输工程来看，专线确实是晚高峰稳定的必要基石，但绝不是无条件充要条件。

### 1. IEPL、IPLC 与 BGP 中转的真实稳定性边界
- **IEPL / IPLC 专线为何抗拥堵？**：普通公网直连和部分普通公网隧道中转，跨境段必须经过电信 `163`、联通 `4837` 或移动 `CMI` 的民用公网国际出口，晚高峰拥堵与防火墙干扰集中发生在这里。而正规的 **IPLC（国际私有租用线路）** 与 **IEPL（国际以太网专线）** 从国内机房点对点直通香港/新加坡等境外机房内网，物理路径不经过民用公网拥堵口，因此在跨境段具有极低的丢包率和抖动。技术原理解析见 [IEPL 专线原理](/routes/iepl/) 与 [IPLC 国际专线](/routes/iplc/)。
- **为什么同样标“IEPL”，有的机场晚上还是卡？**
  1. **入口端单线超售**：哪怕后半段专线是真的，如果前置国内入口机房只有 1Gbps 带宽却卖给了上千个同时开着 4K 视频的用户，卡顿一样发生在国内入口侧。
  2. **跨网接入瓶颈**：很多中低价位机场的国内入口机房是单线电信或单线联通。如果你家里用的是移动宽带去连一台没有 BGP 优化的纯电信入口，晚高峰跨网互联节点本身就会丢包 10% 以上。此时选择带有 **BGP 多线智能调度或三网优化入口** 的方案（例如库内标注 BGP 调度的 [暮光加速](/brands/muguang/)、[SOGO 云](/brands/sogo/)、[全球云](/brands/quanqiu/) 等方向，具体均需以本地实测为准）往往比单纯看“IEPL”四个字更切实际。
  3. **落地 IP 质量与解锁压力**：如果同一批用户把香港、日本落地节点用来跑高并发爬虫、大流量挂机或频繁刷流媒体，落地服务器会被上游机房限速甚至临时拉黑。

### 2. 传输协议对弱网与晚高峰丢包的补偿能力
在协议层面，不同协议在晚高峰的耐受度差异明显：
- **`VLESS-Reality` / `Trojan`**：基于 TCP + TLS 传输，优点是连接极为稳健、极少遭到运营商针对 UDP 的限速打击、路由器与低功耗设备 CPU 占用极低；缺点是一旦遭遇跨网丢包，TCP 拥塞退避会比较明显。库内如 [一翻云](/brands/yifan/)、[可信云](/brands/kexin/)、[速界](/brands/sujie/)、[光年梯](/brands/guangnian/)、[微风网络](/brands/weifeng/)、[二猫云](/brands/ermao/) 均采用了 `VLESS`，[星岛梦](/brands/xingdaomeng/) 与 [唯兔云](/brands/weitu/) 标注了 `Trojan`。
- **`Hysteria 2`**：基于 QUIC（UDP）加上针对弱网设计的 Brutal 拥塞控制，在本地 Wi-Fi 信号差、校园网丢包或晚高峰跨网抖动高达 5% 的环境下，往往能强行维持高单线程下载吞吐。但它的边界在于部分省市的运营商宽带在晚高峰会对高带宽 UDP 流量进行阶段性 QOS 限流。因此，像 [一翻云](/brands/yifan/) 这种同时提供 `Hysteria 2` 与 `VLESS-Reality` 的多协议订阅，在晚高峰应对不同网络环境时回旋余地更大。

## 五、高可用防断流实战：客户端主备 Fallback 与分流隔离配置

没有任何一家机场能够保证 365 天 24 小时永不维护或零故障。把单点稳定性做到 99.9% 的工程正解，不是祈祷某一家神仙机场永远不坏，而是在客户端建立**“主力月付 + 异构不限时备用”的自动容灾机制**。

### 1. 异构主备双机场采购原则
在配置主备前，必须遵守一条底线——**主备两家机场必须支持第三方通用订阅，且绝不能买在同一套同源模板上**（例如避开同时采购 [大佬云](/brands/dalaoyun/)、[闪电鼠](/brands/shandianshu/)、[云界线](/brands/yunjiexian/)、[榴莲云](/brands/liulianyun/)、[环球梯](/brands/huanqiuti/) 这五家高度重合的 5.6 元集群，因为它们一旦上游共用节点出问题可能同时瘫痪）。

推荐组合思路：
- **主力通道**：选择一家支持第三方订阅且你本地晚高峰实测稳定的月付套餐（如 100GB–300GB/月档位），承载日常 95% 的网页、开发与 4K 视频流量。
- **应急备用通道**：配置一个按量计费、永不过期的[不限时流量包](/plans/non-expiring/)（例如库内支持通用订阅或兼容排查的 [一翻云](/brands/yifan/) ¥100/100GB、[光速云](/brands/guangsuyun/) ¥147/247GB、[星岛梦](/brands/xingdaomeng/) ¥100/100GB 或 [唯兔云](/brands/weitu/) ¥100/100GB），平时几乎不消耗额度，专在主力节点割接或晚高峰突发抖动时顶上。

### 2. Mihomo / Clash Verge Rev 的科学 `fallback` 策略组写法
许多用户习惯把所有节点丢进一个 `url-test` 自动测速组，结果一到晚高峰延迟稍微波动，客户端每隔 5 分钟就把出口 IP 从“日本 01”跳到“新加坡 03”再到“美国 02”。这种做法有两个致命隐患：**第一，正在进行的 SSH 终端、网盘上传和网页下载会瞬间断开；第二，ChatGPT 与 Claude 检测到你的账号在 10 分钟内横跨三个国家 IP，极大概率直接触发风控封号。**

正确的稳定配置应当将“常规代理”和“AI 固定出口”拆分为两组，并合理使用 `fallback`（故障转移：只有当前主力组彻底不可用超时后，才按顺序切换到备用，平时死守第一顺位）：

```yaml
# 在 Clash Verge Rev 全局扩展脚本或 Merge 覆写中配置稳态故障转移组
proxy-groups:
  # 1. 日常网页与开发主力组：采用 fallback（优先走香港低延迟组，主机场全挂才切备用机场）
  - name: "🚀 日常稳态主备"
    type: fallback
    url: "https://cp.cloudflare.com/generate_204"
    interval: 180        # 检测间隔拉长到 3 分钟，避免无意义频繁探测
    lazy: true           # 无流量时不后台空跑测速，省电省并发
    proxies:
      - "主力机场-香港稳态"
      - "主力机场-日本稳态"
      - "备用不限时机场-保底节点"

  # 2. 主力内部选优组：仅用于同地区节点择优，加大 tolerance 容忍度防止反复横跳
  - name: "主力机场-香港稳态"
    type: url-test
    url: "https://cp.cloudflare.com/generate_204"
    interval: 300        # 5 分钟检测一次
    tolerance: 80        # 只有新节点比当前节点快 80ms 以上才允许切换（核心防抖参数）
    lazy: true
    proxies:
      - "主力-香港IEPL-01"
      - "主力-香港IEPL-02"

  # 3. AI 专用防风控组：严禁自动跳节点！采用 select 手动锁定单一纯净美国/日本节点
  - name: "🤖 AI 固定防风控"
    type: select
    proxies:
      - "主力-美国原生-01"
      - "主力-日本纯净-02"
      - "备用-美国节点-01"
```

注意上述配置中的 `tolerance: 80` 和 `lazy: true`——这两个参数是防止客户端“假性不稳定”的工程核心。设置 `tolerance: 80` 后，只要当前使用的节点延迟在正常波动范围内（比如从 45ms 跳到 75ms），客户端绝不会主动掐断你的长连接去切到另一个 40ms 节点；关于更多配置文件合并与分流技巧，可继续阅读 [Clash 配置文件结构与覆写指南](/guides/clash-config/) 与 [分流规则深度教程](/guides/routing/)。

## 常见问题（FAQ）

### 为什么客户端列表测出来的“40ms 延迟”不能代表机场晚高峰稳定？
客户端自带的测延迟通常是单次 HTTP `204` 请求或简单的 TCPing 快照，只捕捉测速那一瞬间的连接建立耗时，无法反映连续 100 个数据包是否存在丢包与抖动，也测不出 4K 视频持续拉流时的中转端口限速或单线程吞吐衰减。

### 晚高峰测试机场稳定性，为什么优先看单线程速率而不是多线程测速？
日常打开网页、加载 GitHub 仓库、使用 [ChatGPT](/ai-streaming/chatgpt/) 或 [Claude](/ai-streaming/claude/) 的 SSE 流式输出以及播放 YouTube 4K 视频，底层主要依赖单条或极少数几条 TCP/QUIC 长连接。多线程测速可以通过并发连接掩盖单连接限速和拥塞窗口退避，只有单线程持续下载速率与 HTTP TTFB 才能反映真实使用体感。

### 延迟 30ms 但有 3% 丢包的香港节点，和延迟 90ms 但 0% 丢包的日本节点选哪个？
毫不犹豫选择 0% 丢包的日本节点。现代 TCP 拥塞控制算法（如 CUBIC 或 BBR）对丢包极为敏感，3% 至 5% 的随机丢包会持续触发重传与发送窗口回退，导致单线程带宽雪崩和 AI 对话断流；而稳定 90ms 且零丢包的链路，网页加载和 4K 视频拖动依然极其跟手。

### 只要机场宣传用了 IEPL 或 IPLC 专线，晚高峰就一定稳吗？
不一定。IEPL 和 IPLC 虽然在跨境传输段绕开了公网国际出口拥堵，但整条链路的稳定性仍取决于三个条件：国内入口机房在晚高峰是否超售、你的本地宽带（如移动或电信）接入入口机房是否跨网绕路、以及海外落地机房的出口质量。入口超售严重的专线，晚上照样会高丢包和限速。

### 数据库里的 2026-10-19 测速数据可以用来判断哪家机场晚高峰更稳吗？
不能。库内 15 家品牌收录的 `2026-10-19` 测试表格明确标注为**非晚高峰历史汇总记录**，且缺失测速工具名称、线程数与本地宽带运营商信息（香港高度集中在 `477–548 Mbps`、美国集中在 `14–30 Mbps`）。它只能证明历史上曾测过对应地区节点，真正的晚高峰稳定性必须由你在自己宽带的 `20:00–23:30` 实测。

### 如何在客户端配置主备自动切换（Fallback），同时避免触发 AI 账号风控？
在 [Clash Verge Rev](/clients/clash-verge-rev/)、[Mihomo](/clients/mihomo/) 或 [OpenClash](/clients/openclash/) 中，可以将日常网页与视频组设为 `url-test`（注意加上 `tolerance: 80` 防抖）或 `fallback`，但专门针对 ChatGPT、Claude 与 Gemini 的 AI 策略组绝对不能绑定高频自动测速组，而应采用“手动锁定单一纯净节点”的 `select` 策略组，防止几分钟换一次出口 IP 导致账号被封。

### 晚高峰测试发现 Hysteria 2 比 VLESS 更快，是不是所有场景都该用 Hysteria 2？
在本地宽带存在跨网丢包或学校宿舍网拥堵时，基于 QUIC UDP 的 `Hysteria 2` 往往能靠激进拥塞控制跑出比 TCP 类协议更高的单线程速度；但部分地区运营商会在晚高峰对高流量 UDP 实施 QoS 限速或阻断，此时支持双协议并存（如 [一翻云](/brands/yifan/) 同时提供 `VLESS-Reality` 与 `Hysteria 2`）的机场会更具抗波动韧性。
