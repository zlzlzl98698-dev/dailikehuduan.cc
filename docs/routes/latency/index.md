# 低延迟节点、丢包与机场测速口径详解：ICMP/TCPing/TLS RTT/HTTPS 204 差异、8 倍单位换算与晚高峰标准化脚本

<div class="answer-first-label">核心结论 · Answer First</div>
<p>判断一条代理节点“快不快、稳不稳”，最危险的误区就是<strong>只看客户端列表里测出来的一个“毫秒数”或一张白天的峰值测速图</strong>。在现代中转与专线架构下，<strong>ICMP Ping</strong> 与 <strong>TCPing</strong> 极易制造“假低延迟”；只有走完完整代理加密隧道并抵达海外测试目标的 <strong>TLS RTT 与 HTTPS <code>generate_204</code> 全链路首包耗时（TTFB）</strong> 才贴近真实网页响应速度。决定 4K 视频与 AI 对话流畅度的核心，永远是<strong>晚高峰（20:00–23:30）的丢包率、连续抖动（Jitter）与单线程吞吐</strong>。同时，对比任何品牌测速表前，必须先执行 <code>1 MB/s = 8 Mbps</code> 单位换算，并严格区分 <code>historical</code>（非晚高峰历史摘要）与 <code>measured</code>（附带测试条件的实测归档）。</p>

## 一、四种延迟测量口径技术拆解：为什么显示 30ms 却打不开网页？

打开 [Clash Verge Rev](/clients/clash-verge-rev/)、[v2rayN](/clients/v2rayn/)、[Shadowrocket](/clients/shadowrocket/) 或各类第三方测速脚本，屏幕上跳出的 `32ms`、`45ms` 往往对应四种完全不同的网络层测量动作。在三段式代理架构（**第一段：本地宽带 → 境内入口；第二段：境内入口 → 海外落地；第三段：海外落地 → 目标网站**）中，每种口径测量的物理区间截然不同。

### 1. 四类延迟口径的技术覆盖与盲区对比

| 测量口径 | 网络层与实际执行动作 | 是否经过加密协议认证 | 是否穿透境内入口并抵达海外落地 | 常见误导与“假低延迟”失效场景 |
| :--- | :--- | :--- | :--- | :--- |
| **1. ICMP Ping** | 本机直接向节点服务器域名/IP 发送 `ICMP Echo Request` | **否** | **否**（仅测本机到第一跳入口服务器） | 1. 许多中转前置机为防扫描直接禁 Ping，导致全部显示 `Timeout` 但实际上网飞快；<br>2. 国内中转机距你仅 15ms，即使它背后的跨境海缆已经断网，Ping 值依然漂亮得惊人。 |
| **2. TCPing（真连接前阶）** | 本机向节点入口 IP 的指定端口发起 TCP `SYN → SYN/ACK` 三次握手 | **否**（不校验 UUID/密码） | **否**（仅确认入口机端口处于监听状态） | **最常见的“30ms 假正常”元凶**：只要境内中转机端口没关，哪怕机场主忘了续费海外落地机、或加密密码填错、或跨境管道彻底阻塞，TCPing 依然显示 20ms–40ms 绿色健康。 |
| **3. TLS RTT（加密握手延迟）** | 完成 TCP 三次握手后，继续发起完整 `ClientHello → ServerHello` TLS 密钥协商 | **部分**（验证协议入口与证书响应，不代表后端转发通畅） | **取决于架构**（直连节点可到落地；中转节点常由入口机前置 TLS 终止或透传） | 能排查本机时间偏差导致的证书错误（见 [系统时间与 TLS 修复](/guides/system-time-tls-fix/)）以及部分 SNI 阻断；但若中转机在本地先行完成 TLS 卸载（TLS Termination），仍无法测出跨境段卡顿。 |
| **4. HTTPS `generate_204` 全链路 TTFB（URL-Test）** | 通过完整代理客户端隧道加密发送请求，经境内入口与跨境段到达海外落地机，再向外部测试端点（如 `cp.cloudflare.com/generate_204`）发出 HTTP GET 并等待首个字节返回 | **是**（完整验证 UUID、加密套件与服务端转发） | **是**（完整涵盖第一、二、三段全链路） | **唯一贴近真实浏览体感的指标**；需注意在包含首次建连的测量中，总耗时内含“国内 TCP + 跨境通道 + TLS 握手 + 海外落地到 Cloudflare 边缘”的总和，因此美国节点 URLTest 通常比 TCPing 高出 150ms–300ms 属于正常物理规律。 |

### 2. 为什么客户端软件测出来的 URL-Test 还是比网页打开慢或快？

在 [Mihomo](/clients/mihomo/) 或 [sing-box](/clients/sing-box/) 内核中，点击“测速”执行的通常是 **统一测试（Unified Delay / URL-Test）**。理解两个细节可以避免误判：
1. **首次冷启动建连 vs 复用连接耗时**：初次对一个休眠节点测 `generate_204`，往往包含本机到入口的 TCP 握手（1 个 RTT）以及代理链路到目标站的 TLS 握手（1–2 个 RTT），因此“真连接延迟”通常是纯底层物理 RTT 的 **2 到 3 倍**。例如一条物理 RTT 仅 25ms 的香港节点，首次 `generate_204` 测出 60ms–90ms 完全正常；而若开启了长连接复用（HTTP Keep-Alive / Multiplex），后续请求才会回落到接近物理单程往返的 25ms–35ms。
2. **国内入口 DNS 缓存与测试 URL 差异**：有些客户端使用 `http://www.gstatic.com/generate_204`（未走 TLS 的明文 HTTP），而现代网站几乎全部使用 HTTPS。如果某节点对 80 端口放行、对 443 端口实施了特征干扰或落地的 HTTPS 出站受阻，明文 204 测速会通过，实际浏览 HTTPS 网站却照样转圈。因此强烈建议将客户端测速地址统一设为 **`https://cp.cloudflare.com/generate_204`**。

### 3. 命令行分段诊断：看清耗时究竟卡在三段中的哪一段

当你遇到“客户端显示 35ms，但浏览器访问网站半天打不开”时，不要盲目重启路由器。在电脑终端里用系统自带的 `curl` 通过代理端口（[Clash Verge Rev](/clients/clash-verge-rev/) 默认混合端口为 `7897`，v2rayN 默认为 `10808`）输出分段计时指标，3 秒就能定位病灶：

```bash
# 通过本地代理端口请求 HTTPS 204，精准拆分 TCP 建连、TLS 握手、首包等待(TTFB)与总耗时
curl -x http://127.0.0.1:7897 -o /dev/null -s -w \
"本地到代理端口(TCP): %{time_connect}s\n端到端TLS协商完成: %{time_appconnect}s\n海外返回首包(TTFB): %{time_starttransfer}s\n请求总耗时: %{time_total}s\nHTTP状态码: %{http_code}\n" \
https://cp.cloudflare.com/generate_204
```

**判读方法**：
- `time_connect` 只有 `0.002s`（因为 `curl` 的 TCP 握手是跟本机 `127.0.0.1:7897` 完成的），关键看 `time_appconnect` 与 `time_starttransfer` 之间的差值。
- 如果 `time_appconnect` 高达 `2.500s` 甚至超时（`http_code` 为 `000`），说明**本地到境内入口、跨境过境或海外 TLS 握手阶段已经严重丢包或被阻断**（进一步排查见 [节点全部 Timeout 排查](/troubleshooting/timeout/)）。
- 如果 `time_appconnect` 很快（如 `0.120s`），但 `time_starttransfer` 到 `time_total` 卡了数秒才返回，或者把目标换成实际网站（如 `https://api.github.com`）时 `time_starttransfer` 暴涨，说明**代理隧道本身没断，但海外落地机的国际出海带宽拥堵或遭遇了目标站点限流/风控校验**。

## 二、低延迟 ≠ 高流畅：丢包率、抖动（Jitter）与单线程吞吐的数学制约

为什么物理延迟只有 35ms 的节点，看 YouTube 4K 依然会降级到 480P 甚至断流缓冲？答案藏在 **TCP 拥塞控制与丢包降速数学模型（Mathis Equation）** 中。

### 1. 丢包对高带宽延迟积（BDP）链路的毁灭性打击

在传统基于 TCP 协议的传输链路中，单条 TCP 连接所能达到的理论最大吞吐量与**丢包率（$p$）的平方根**和**往返时延（$\text{RTT}$）**成反比：

$$\text{最大单连接吞吐} \approx \frac{\text{MSS} \times C}{\text{RTT} \times \sqrt{p}}$$

其中 $\text{MSS}$（最大报文段长度）常规约为 1460 字节。我们把具体数字代入即可看清“低延迟却极卡”的真相：
- **场景 A（零丢包 / 0.01% 极微丢包，RTT = 50ms）**：在主流 BBR 拥塞控制下，单连接即可轻松跑出 **150–400 Mbps**（约 18.75–50 MB/s），看 4K/8K 视频进度条随便拖动秒缓冲。
- **场景 B（RTT 同样仅 35ms，但晚高峰出现 3% 丢包）**：即使延迟只有 35ms，3% 的连续丢包会让标准 TCP 拥塞窗口频繁遭遇超时重传（RTO）与快速重传，把窗口反复削减到极小值。此时单条 TCP 连接的实际吞吐会被瞬间压制到 **2–6 Mbps**（不足 1 MB/s），连流畅播放 1080P 60fps 都勉强，4K 视频必然转圈！
- **场景 C（低延迟下的“协议内卷”放大效应）**：如果代理协议本身采用 `TCP-over-TCP`（即外层 TCP 隧道里包裹内层浏览器 TCP 连接），在境外无丢包的专线环境下影响极微；一旦第一跳公网或跨境段发生晚高峰丢包，就会触发著名的 **TCP Meltdown（TCP 熔断重传雪崩）**，表现为延迟测出来只有 40ms，网页却彻底卡死、必须断开重连才能恢复几秒。

### 2. 延迟抖动（Jitter）与 P95/P99 长尾卡顿

**抖动（Jitter）** 指的是连续多次请求之间往返耗时的离散波动幅度。假设连续测 20 次请求：
- **线路甲（稳定慢但零抖动）**：20 次全部稳稳落在 **68ms–75ms** 之间（抖动仅 7ms）。虽然绝对延迟不如香港，但每次点击链接、发送 AI 对话提示词、打游戏按技能的响应极其线性可预期，体感非常丝滑。
- **线路乙（平均低但高抖动）**：16 次在 **28ms–35ms**，但有 3 次突然跳到 **480ms**、1 次超时 **2100ms**。尽管平均值算出来好看，但现代一个普通网页包含数十个并发 CSS/JS/API 请求，只要其中 1–2 个核心脚本撞上了那 5% 的长尾超时，整个网页就会一直白屏转圈等待渲染。这就是为什么**晚高峰连续 20 次测试中的最大值（P95/Max）和失败次数，比平均延迟重要十倍**。

### 3. 单线程 vs 多线程测速陷阱：为什么跑分 800 Mbps 看视频还卡？

市面上很多机场评测图喜欢贴出 Speedtest 8 线程或 16 线程跑出的“800 Mbps”截图，甚至以此宣传“千兆不限速”。然而在真实上网中：
- 打开网页、加载 ChatGPT 流式输出（SSE）、观看 Netflix/YouTube 视频缓冲、拉取 GitHub 单一仓库、用浏览器直接下载文件，绝大多数情况都是 **单线程（1 Thread）或双线程并发**。
- 当某些超售机场在路由器层面对单连接做了限速（例如限制单条 TCP 连接最多只能跑 15 Mbps），或者跨境段存在轻微排队丢包时，单线程下载只能跑出 **1.8 MB/s**；但测试者一旦把线程数开到 16 个同时向 16 条端口抢占带宽，16 × 15 Mbps = 240 Mbps，面板瞬间变成一条好看的大数字！
- **工程验收原则**：评价节点日常体验，**只看单线程稳定速率曲线 + 晚高峰连续 20 次 HTTPS 204 零超时**；多线程跑分仅能测出服务器网卡总上限，不能反映单用户交互流畅度。

## 三、带宽速率单位换算标准（`1 MB/s = 8 Mbps`）与数据库实证判读

无论是查看客户端左下角的实时网速浮窗，还是核对本站或第三方评测记录里的带宽数值，**大小写字母 `b` 与 `B` 的混淆** 是引发“机场是不是虚标速度”争论的头号原因。

### 1. 国际标准换算公式与常见场景对应表

- **`Mbps`（Megabits per second，兆比特/秒，小写 `b`）**：中国电信/联通/移动宽带标称速率（如 500M、1000M 宽带）、Speedtest CLI 与绝大多数机场测速脚本使用的标准单位。
- **`MB/s`（Megabytes per second，兆字节/秒，大写 `B`）**：Chrome/Edge 浏览器下载进度条、IDM、Steam 下载、Windows 任务管理器及 Clash Verge Rev / v2rayN 实时速率面板显示的单位。
- **严谨换算公式**：因为计算机存储中 `1 Byte = 8 bits`，所以 **`1 MB/s = 8 Mbps`**（反过来，`1 Mbps = 0.125 MB/s`）。（注：扣除约 5%–8% 的 TCP/IP 与代理加密协议头封装开销后，100 Mbps 链路实际有效载荷下载通常在 11.5–12.0 MB/s 左右）。

| 测速工具显示速率（Mbps） | 理论文件下载速率（MB/s） | 扣除协议开销后常见有效下载（MB/s） | 真实使用场景对应能力评估 |
| :--- | :--- | :--- | :--- |
| **16 Mbps** | 2.0 MB/s | 约 1.8 MB/s | 流畅浏览网页、AI 对话、YouTube 1080P（若无丢包可勉强缓冲部分低码率 4K） |
| **25 Mbps** | 3.125 MB/s | 约 2.8 MB/s | 满足单台设备稳定观看常规 YouTube 4K 30fps（对应流媒体建议底线） |
| **50 Mbps** | 6.25 MB/s | 约 5.7 MB/s | **单人主力合格线**：流畅观看 YouTube 4K 60fps、Netflix 4K HDR、日常高频同步 |
| **100 Mbps** | 12.5 MB/s | 约 11.5 MB/s | 家庭 2–3 台设备同时观看 4K 流媒体、大中型开源项目拉取与远程桌面 |
| **160–640 Mbps** | **20–80 MB/s** | 约 18.5–74 MB/s | 对应灵动云 `2026-07` 实测区间：轻松跑满多数百兆至五百兆家庭宽带 |

| **1000 Mbps（1 Gbps）** | **125 MB/s** | 约 115 MB/s | 跑满千兆家庭宽带理论物理上限；对客户端 CPU 单核 AES/ChaCha20 加解密性能要求极高 |

## 四、晚高峰（20:00–23:30）标准化自测脚本与四维验收标准

当你购买了一个支持 [月付短周期](/plans/monthly/) 或试用的机场准备长期使用前，最科学的做法是在 **工作日晚高峰 20:30–22:30** 之间，用自己家里的主力宽带（不要去公司千兆专线测）运行以下标准化两段式自测：

### 1. 第一步：连续 20 次 HTTPS `generate_204` 抖动与丢包压测

请先将代理客户端切换到待测的单个节点（例如 `香港 02` 或 `日本 01`），然后执行与你系统对应的脚本（以本地 HTTP 代理端口 `7897` 为例，若用 v2rayN 请改为 `10808`）：

**Windows PowerShell 标准化脚本：**

```powershell
# 晚高峰连续 20 次 HTTPS 204 延迟、抖动与丢包统计脚本（默认端口 7897）
$proxy = "http://127.0.0.1:7897"
$url = "https://cp.cloudflare.com/generate_204"
$times = @()
$fail = 0

1..20 | ForEach-Object {
  $res = curl.exe -x $proxy --connect-timeout 3 --max-time 6 -o NUL -s -w "%{http_code}|%{time_appconnect}|%{time_starttransfer}" $url
  $parts = $res -split '\|'
  if ($parts[0] -eq "204") {
    $ttfbMs = [math]::Round([double]$parts[2] * 1000, 1)
    $tlsMs = [math]::Round([double]$parts[1] * 1000, 1)
    $times += $ttfbMs
    Write-Host ("第 {0:D2} 次 | HTTP 204 | TLS完成: {1}ms | 首包TTFB: {2}ms" -f $_, $tlsMs, $ttfbMs)
  } else {
    $fail++
    Write-Host ("第 {0:D2} 次 | 超时或失败 (状态码: {1})" -f $_, $parts[0]) -ForegroundColor Red
  }
  Start-Sleep -Milliseconds 400
}

if ($times.Count -gt 0) {
  $sorted = $times | Sort-Object
  $avg = [math]::Round(($times | Measure-Object -Average).Average, 1)
  $min = $sorted[0]
  $max = $sorted[-1]
  $jitter = [math]::Round($max - $min, 1)
  Write-Host "`n--- 汇总结果 ---" -ForegroundColor Cyan
  Write-Host "成功次数: $($times.Count)/20 | 失败丢包数: $fail"
  Write-Host "最小TTFB: ${min}ms | 平均TTFB: ${avg}ms | 最大TTFB: ${max}ms | 极差抖动(Jitter): ${jitter}ms"
}
```

**macOS / Linux Bash 标准化脚本：**

```bash
#!/usr/bin/env bash
PROXY="http://127.0.0.1:7897"
URL="https://cp.cloudflare.com/generate_204"
FAIL=0

for i in $(seq -w 1 20); do
  OUT=$(curl -x "$PROXY" --connect-timeout 3 --max-time 6 -o /dev/null -s -w "%{http_code}|%{time_appconnect}|%{time_starttransfer}" "$URL")
  CODE=$(echo "$OUT" | cut -d'|' -f1)
  TLS=$(echo "$OUT" | cut -d'|' -f2)
  TTFB=$(echo "$OUT" | cut -d'|' -f3)
  if [ "$CODE" = "204" ]; then
    TLS_MS=$(awk "BEGIN {printf \"%.1f\", $TLS*1000}")
    TTFB_MS=$(awk "BEGIN {printf \"%.1f\", $TTFB*1000}")
    echo "第 ${i} 次 | HTTP 204 | TLS完成: ${TLS_MS}ms | 首包TTFB: ${TTFB_MS}ms"
  else
    FAIL=$((FAIL+1))
    echo "第 ${i} 次 | 超时或失败 (状态码: ${CODE})"
  fi
  sleep 0.4
done
echo "压测结束，失败/超时次数: ${FAIL}/20"
```

### 2. 第二步：单线程 50MB / 100MB 大文件实测（验证单连接稳态速度）

完成 20 次低抖动验证后，使用 `curl` 发起一次**严格单线程**的 50MB 测试包下载（仅测试一次约消耗 50MB 流量，若节点为高倍率请先核实倍率后再测）：

```bash
# 单线程下载 Cloudflare 50MB 测试包并输出平均下载字节速率（需自行将字节数换算为 MB/s 与 Mbps）
curl -x http://127.0.0.1:7897 --max-time 30 -o /dev/null -w \
"状态码: %{http_code} | 耗时: %{time_total}s | 平均单线程速率: %{speed_download} Bytes/s\n" \
"https://speed.cloudflare.com/__down?bytes=52428800"
```

（注：将输出结果的 `Bytes/s` 除以 `1048576` 即得到 `MB/s`；再乘以 `8` 即可对比宣传中的 `Mbps` 数值。例如输出 `26214400 Bytes/s`，除以 1048576 等于 **25 MB/s**，乘以 8 即为 **200 Mbps**。）

### 3. 第三步：晚高峰四维验收判读标准

| 评估等级 | 20 次 HTTPS 204 失败率 | 极差抖动（Max - Min） | 晚高峰单线程下载速率 | 实际体验结论与处置建议 |
| :--- | :--- | :--- | :--- | :--- |
| **一线主力（优质专线 / 轻载优化）** | **0/20（0% 失败）** | 亚太节点 **低于 35ms** | **≥ 12.5 MB/s（100+ Mbps）** | 4K 60fps 秒拖、AI 流式回复无停顿、远程 SSH/Git 极其跟手，可作长期主力。 |
| **合格可用（主流商业标准）** | **0/20（0% 失败）** | 亚太节点 **35ms – 80ms** | **5–12 MB/s（40–96 Mbps）** | 足以满足单人 4K 观影与办公；部分时刻轻微波动，但不断流。 |
| **轻度超售 / 跨网拥堵** | **1–2 次超时（5%–10%）** | 波动高达 **150ms – 500ms** | **1.5–4.5 MB/s（12–36 Mbps）** | 网页偶现转圈刷新、4K 视频会降码率；建议检查是否跨网访问了单线入口，或切换冷门编号节点。 |
| **重度超售 / 假专线不可用** | **≥ 3 次超时（15%+）** | 动辄跳变 **1000ms+** | **低于 1 MB/s（8 Mbps 以下）或中断** | 白天测速再快也无意义，晚高峰无法正常办公与观影，切勿续费或购买年付。 |

### 4. 客户端测速组调优：防止 `url-test` 盲目切点导致断流

很多用户明明有一组不错节点，却总是感觉每隔几分钟网页突然卡死 5 秒，原因往往出在客户端 `url-test` 策略组参数设置过于激进：
- **调大 `tolerance`（容差阈值）**：在 [Clash 配置](/guides/clash-config/) 中，默认若不设 `tolerance`，只要节点 B 比正在用的节点 A 快 2ms，内核就会立刻断开当前长连接切换节点，导致 AI 对话中途报错或视频重缓冲。**建议将 `tolerance` 设为 `40` 至 `60`（毫秒）**，只有当备用节点快出 50ms 以上时才触发切换。
- **合理拉长 `interval`（测速间隔）**：将 `interval` 设为 `300`（每 5 分钟）或 `600`（每 10 分钟），并开启 `lazy: true`（仅在有流量经过该策略组时才测速），既能避免后台高频无效测速浪费流量、触发机场并发风控，又能稳住长连接体验（详见 [晚高峰稳定性评估](/airport/stable/)）。

## 常见问题（FAQ）

### 1. 为什么代理客户端里显示节点延迟只有 30ms，打开网页和看 4K 视频却依然卡顿转圈？
客户端内默认的 TCPing 或单次 URLTest 只反映了某一次握手的往返耗时（RTT），不能反映链路的丢包率、延迟抖动（Jitter）和可用单线程带宽。如果节点在晚高峰存在 3% 至 5% 的持续丢包，TCP 拥塞控制算法（如 CUBIC）会频繁触发重传并强制将发送窗口减半，使实际单连接吞吐暴跌至几 Mbps 甚至几百 Kbps，从而出现延迟数字很低但网页打不开、视频不停转圈的现象。

### 2. ICMP Ping、TCPing、TLS RTT 和 HTTPS 204（TTFB）四种延迟测量口径有什么本质区别？
ICMP Ping 和 TCPing 均不经过代理密码校验和海外落地机：ICMP Ping 仅测本地到节点入口 IP 的网络层通断，很多中转机禁 Ping；TCPing 仅测入口服务器端口是否开放，即便后端落地已断线或账号过期也会显示几十毫秒的假正常。TLS RTT 进一步校验加密握手耗时但未计入目标服务器返回响应；只有 HTTPS `generate_204` 全链路 TTFB 跑完了本地宽带到境内入口、跨境通道再到海外落地访问目标测试端点的完整路径，最接近日常浏览体感。

### 3. 为什么机场测速表写着 500 Mbps，我实际用浏览器或下载工具跑出来只有 60 MB/s 左右？
这是网络速率单位与文件传输单位的 8 倍换算关系，并非服务商虚标。运营商宽带、Speedtest 与机场测速脚本通常使用小写的兆比特每秒 `Mbps`（Megabits per second），而浏览器、Windows 资源管理器和客户端流量浮窗使用大写的兆字节每秒 `MB/s`（Megabytes per second）。由于 `1 Byte = 8 bits`，换算公式为 `1 MB/s = 8 Mbps`，因此 `500 Mbps` 的理论满速恰为 `62.5 MB/s`。

### 4. 如何正确看待本站 `brands.ts` 数据库中 15 家品牌的 `2026-10-19` 测速汇总表？
本站 `2026-11-23` 数据库快照中收录的 15 家品牌（如 [光速云](/brands/guangsuyun/)、[暮光加速](/brands/muguang/)、[飞猫云](/brands/feimao/)、[一翻云](/brands/yifan/) 等）五地区延迟与 Mbps 数据，源自 `2026-10-19` 原文标注的非晚高峰历史汇总记录（`evidence` 等级为 `historical`）。它缺少测试软件名称、单线程或多线程参数及本地宽带运营商信息，仅能作为当年非晚高峰状态下的横向基准参考，绝不能直接等同于你今天在晚高峰本地宽带的实时速度保证。

### 5. 灵动云在 `2026-07` 实测中跑出了 20–80 MB/s 的下载速率，为什么记录里仍然标注了多项风险问题？
[灵动云](/brands/lingdong/) 在 `2026-07-20` 至 `2026-07-21` 珠海联通 9Gbps 环境下完成了 60 节点实测（归档于 `2026-08-09` 品牌库，`evidence` 等级为 `measured`），全节点下载速率 `20–80 MB/s`（按 8 倍换算约为 `160–640 Mbps`），峰值带宽表现不俗。但该实测同时暴露了 HTTPS 延迟偏高、美国 01 整节点失败、TikTok 多节点失败以及新加坡和台湾节点 YouTube 送中等问题。这恰恰证明峰值下载带宽只是评测的一个维度，绝不能用单一高下载速率掩盖高延迟、部分节点失效和流媒体送中短板。

### 6. 测速时应该用单线程还是多线程？为什么很多机场测试图能轻松跑满千兆？
日常打开网页、使用 ChatGPT/Claude 对话、观看 YouTube 4K 或拉取 Git 代码，绝大多数场景依赖单条或少数几条 TCP/QUIC 连接，因此单线程下载速度与连续波动曲线最真实。多线程测速（同时开启 8 到 32 条并发连接）在多线拥堵的超售线路上可以通过抢占连接数把总带宽拉高，从而掩盖单连接已被运营商限速或高度丢包的真相。

### 7. 普通用户没有专业服务器，怎么在晚高峰 20:00–23:30 自己测出一条线路稳不稳？
不需要运行复杂的并发测速面板。只要在工作日晚高峰 20:30 至 22:30 之间，使用系统自带的 `curl` 命令通过本地代理端口连续请求 20 次 Cloudflare 的 `generate_204` 接口，统计成功次数、TTFB 中位数与最大最小值差（抖动），再单线程下载一个 50MB 或 100MB 测试文件观察实时速率是否稳定、有无瞬间掉零，即可高置信度判定节点在晚高峰是否可靠。
