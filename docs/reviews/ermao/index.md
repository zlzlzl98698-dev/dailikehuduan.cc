### 1. 四档月付的「阶梯单价微幅倒挂」拆解

为什么从白猫（¥20）升级到橘猫（¥40）、牛奶猫（¥80）和黑猫（¥160），每 GB 的价格会从 `¥0.154/GB` 一路爬升到 `¥0.188/GB`？
原因在于二猫云采用的是**“入门档加量引流 + 高阶档每次倍增扣减 30GB–40GB”**的定价公式：
- 常规机场的设计是：¥20 给 100GB（¥0.20/GB），¥40 给 220GB（¥0.18/GB），¥80 给 500GB（¥0.16/GB），以此鼓励用户买高价大包。
- 二猫云的做法恰恰相反：为了在竞争最激烈的 [20 元以下月付机场推荐档位](/plans/monthly-under-20-guide/) 中脱颖而出，它把入门档「白猫套餐」直接拉到了 **¥20 / 130GB**。但到了 ¥40 的「橘猫畅玩版」，流量并不是 `130GB × 2 = 260GB`，而是砍掉了 30GB 变成 **230GB**；到了 ¥80 的「牛奶猫尊享版」，流量不是 `230GB × 2 = 460GB`，又砍掉 30GB 变成 **430GB**；到了 ¥160 的「黑猫重度用户版」，流量也不是 `430GB × 2 = 860GB`，再扣 10GB 变成 **850GB**。

**这一精算结论对用户的实际指导价值极大**：
1. **月流量在 130GB 以内的用户**：直接选 **¥20 白猫套餐**，您拿到了全系正价月付里最低的单位流量成本（¥0.154/GB），完全不需要向上多花钱。
2. **月流量在 180GB–250GB 之间的用户**：如果您一个人用，为了省去切换账号的麻烦买 ¥40 橘猫（230GB）尚可接受；但如果是家庭两人分头使用，或者在桌面端与移动端分别配置，**买两份 ¥20 白猫套餐（合计 ¥40 可得 260GB/月）比买一份 ¥40 橘猫套餐（230GB/月）反而多出 30GB 真实配额**。
3. **月流量在 300GB–500GB 以上的重度用户**：二猫云的中高阶月付档（¥80/430GB、¥160/850GB）在单价上并不占优势。作为横向参照，同样宣称 IEPL 专线的 [一翻云](/brands/yifan/) 在 ¥35 档即提供 350GB（¥0.100/GB）、¥55 档提供 600GB（¥0.092/GB）；同样宣称 1 倍流量的 [星岛梦](/brands/xingdaomeng/) 在 ¥70 档提供 500GB（¥0.140/GB）。关于 100GB 与 300GB 以上流量档位的跨品牌选型，可进一步对照 [100GB 与 300GB 流量套餐需求测算指南](/plans/traffic-100gb-vs-300gb/)。

## 三、不限设备连接数与「独家定制客户端」的兼容性边界

在 `32家机场品牌清单.txt`（#7）的原始描述中，二猫云除了强调全线 IEPL 专线与 VLESS 协议外，还重点突出了两项与日常使用体验息息相关的工程属性：**「不限设备连接数」** 与 **「配独家定制客户端」**。这两项属性放在一起，既带来了便利，也潜藏着选型前必须查清的技术边界。

### 1. 「不限设备连接数」对个人多端与家庭场景的实际价值

不少传统机场会严格限制并发在线 IP 或设备数量（例如入门套餐限 2 台或 3 台设备，超出即触发面板封禁或断流）。二猫云声明的 **不限设备连接数**（`vendor` 品牌方宣称），主要解决以下三类高频痛点：
1. **个人全生态多终端无缝常驻**：一名典型的开发者或跨境从业者往往同时拥有公司台式机、随身 MacBook、主力 iPhone、测试用 Android 备用机以及家里的 iPad。不限设备意味着 5–6 台终端可以 24 小时同时挂在后台接收通知，无需出门前手动关掉家里电脑的代理。
2. **软路由/旁路由 + 移动蜂窝网络并行**：当家里配置了全局或规则分流后，家庭宽带算作 1 个公网出口 IP，而家庭成员出门使用 5G 蜂窝流量时各自算作独立的移动公网 IP。不限设备策略能够避免“家里人一开电视，出门在外的人手机就断连”的尴尬。
3. **合理使用边界提醒**：在机场行业，“不限设备数”默认是指**个人或直系家庭范围内的多终端自用**，绝不等于允许将订阅链接或账号密码发到公开群组、论坛或十几个不同省份的陌生人之间大规模合租（面板通常设有异常并发连接数阈值与短时流量激增熔断机制）。详细的并发策略与防封号建议请参阅 [多设备同时在线与家庭共享方案评估](/airport/multi-device/)。

### 2. 「独家定制客户端」vs 第三方通用订阅：下单前头号必查项

为什么我们在 `brands.ts` 数据库中，把二猫云的 `clientMode` 严格标记为 **`待核实`**，并将 `clients` 记为 **`独家定制客户端（是否兼供第三方订阅待核实）`**？

让我们对比一下库内其他品牌的客户端模式：
- **明确双支持（`自研+第三方订阅`）**：如 [光速云](/brands/guangsuyun/)、[梯子云](/brands/tiziyun/)、[大佬云](/brands/dalaoyun/)，它们既有给小白用户一键登录的自研客户端，又在面板保留了“一键导入 Clash / 复制通用订阅链接”按钮。
- **明确锁死专属端（`仅专属客户端`）**：如 [飞猫云](/brands/feimao/)、[隐形人](/brands/yinxingren/)、[SOGO 云](/brands/sogo/)、[Firefly](/brands/firefly/)，它们在资料中明确写死“仅能通过官方专属客户端登录使用，不提供任何第三方订阅链接”。
- **二猫云的表述状态**：二猫云原始资料一方面明确写出了底层传输协议为 **`VLESS`**（而纯封闭专属端品牌如飞猫云、隐形人往往连底层协议都不写），另一方面又强调“配独家定制客户端”，却没有多写半句“是否同时允许导出通用订阅链接”。

这会直接把用户分成两类完全不同的决策路径：
- **如果您是新手或轻度用户**：喜欢下载一个官方客户端、输入账号密码直接点“连接”就能用，不想去研究 YAML 规则、内核切换和订阅转换，那么二猫云的独家定制客户端正好契合您的胃口（但仍需留意客户端下载与权限安全，参见 [专属客户端 vs 第三方通用客户端差异](/airport/client-vs-third-party-subscription/)）。
- **如果您是进阶用户 / 软路由玩家**：日常主力使用 [Clash Verge Rev](/clients/clash-verge-rev/)、[FlClash](/clients/flclash/)、[Mihomo](/clients/mihomo/)、[v2rayN](/clients/v2rayn/)、[Shadowrocket](/clients/shadowrocket/) 或 OpenWrt 上的 [Nikki](/clients/nikki/) / [PassWall 2](/clients/passwall2/)（由于二猫云是 VLESS 协议，需使用支持 Xray/Mihomo/sing-box 内核的客户端），**请务必先用 ¥20 白猫月付登录后台面板，确认仪表盘是否有“复制订阅地址 / 一键导入 Clash”功能**。如果面板已彻底关闭第三方订阅导出，则软路由用户应立即止损，转投明确支持通用订阅的 [光速云](/brands/guangsuyun/) 或 [一翻云](/brands/yifan/)。

### 2. 为什么会出现这种冲突？三种可能性推演

作为独立基础设施分析师，我们不替品牌方掩盖矛盾，而是为您拆解这类档案冲突在机场运营中最常见的三种成因：
- **成因推演 A（早期文案未随节点扩容同步更新）**：二猫云在早期版本（或某一低阶套餐分组）中确实只有港、日、美三地节点，因此早期评测文案写下了“少了新加坡这一站”；后续在 2026 年下半年面板扩容时补齐了新加坡与台湾节点，所以在 `2026-10-19` 统一跑五地测速表时测出了 `46ms / 407Mbps` 和 `41ms / 118Mbps`，但整理清单的人没有删掉旧正文里的那句“少了新加坡”。
- **成因推演 B（不同套餐等级的节点分组权限差异）**：部分机场会将节点池划分为基础组与进阶组——例如年付小包或入门档仅下发港、日、美主力节点，而中高阶月付档才包含新加坡和台湾节点。
- **成因推演 C（2026-10-19 批次测速表的同质化模板填充）**：正如我们在 `audit/data-conflicts.md` 第四节所指出的，主表中 15 家品牌附带的 `2026-10-19 非晚高峰` 五地测速数据（香港普遍 21–27ms / 477–548Mbps、台湾 37–41ms / 100–135Mbps、新加坡 42–46ms / 383–445Mbps、日本 53–57ms / 131–150Mbps、美国 134–180ms / 14–30Mbps）缺乏测试客户端版本、节点编号与本地宽带运营商信息，分布高度接近。因此，**绝不能仅凭这张非晚高峰汇总表就断定二猫云当前一定拥有稳定的新加坡节点**。

### 3. 这项冲突对哪些用户影响最大？

- **如果您主要刷港日流媒体、看 YouTube、查技术文档**：香港（历史参考 22ms）和日本（历史参考 53ms）本就是亚太物理延迟最低的两大核心枢纽（详见 [香港与日本节点延迟对比及选路策略](/routes/hong-kong/) 与 [日本专线节点路由分析](/routes/japan/)），有没有新加坡节点对日常网页和视频体验几乎没有影响。

## 五、全线 IEPL + VLESS 架构声明与 AI / 流媒体解锁风险评估

在传输链路与协议选型上，二猫云的技术标签非常清晰：**全线 IEPL 专线（`vendor`） + VLESS 协议（`vendor`）**。

<NetworkPathDiagram slug="ermao" />

### 1. IEPL + VLESS 组合的技术特点与性能预期

- **IEPL（以太网国际专线）的物理优势**：相比经过公网国际出口（163/CMI 等）的普通直连或公网隧道中转，IEPL 在国内入口（通常为广深或沪浙机房）与海外落地（如香港、日本）之间通过二层以太网内网专线过境，理论上不过公网 GFW 审查点，因此在敏感时期抗封锁能力更强、抖动更低（原理详见 [IEPL 专线原理与鉴别指南](/routes/iepl/) 以及 [IEPL 与 IPLC 专线核心区别](/routes/iepl-vs-iplc-difference/)）。不过需要强调的是，二猫云的“全线 IEPL”属于品牌方资料宣称（`vendor`），且 `2026-10-19` 测速表明确注明为**非晚高峰**记录，其晚高峰（20:00–23:00）的真实带宽冗余仍需用户在本地宽带下实测（测速方法见 [晚高峰稳定性压测指南](/airport/evening-peak-stability-test/)）。
- **VLESS 协议的轻量化特性**：VLESS 去除了 VMess 早期冗余的二次加密开销，配合 TLS 或 Reality 传输层时握手更快、CPU 占用更低，在移动设备（iOS / Android）和高并发连接下表现轻快。但需要注意，旧版 Clash Premium 核心早已停更且不支持新版 VLESS 特性，若导出订阅到第三方软件，客户端必须基于 **Mihomo（Clash.Meta）**、**Xray** 或 **sing-box** 内核。

### 2. AI 与流媒体可用性矩阵：为什么 Claude 与 Gemini 被标为 `conditional`？

<AvailabilityMatrix slug="ermao" />

仔细观察上方的可用性矩阵，您会发现二猫云在流媒体与 AI 服务上的证据分布存在明显分化：
1. **六大主流流媒体（Netflix / Disney+ / YouTube / HBO Max / TikTok / Spotify）**：全部为 `vendor`（品牌方资料标注支持解锁，具体以实际落地节点为准）。
2. **三大主流 AI 大模型（ChatGPT vs Claude vs Gemini）**：
   - **ChatGPT (OpenAI)**：标注为 **`vendor`（品牌方资料标注支持）**。由于二猫云明确拥有日本与美国节点，只要落地 IP 未被 OpenAI 标记为高危滥用机房段，网页端与 API 通常可正常访问（若遇拦截可按 [ChatGPT 地区限制与节点封锁修复指南](/ai-streaming/chatgpt-region-and-block-fix/) 切换节点）。
   - **Claude (Anthropic) 与 Gemini (Google)**：在二猫云的档案中，这两项均被审慎降级为 **`conditional`（视具体节点与时段而定）**，且在 `riskFlags` 中专门警示**“Claude/Gemini 官方未保证可用”**。

**为什么二猫云对 Claude 和 Gemini 不敢像其他品牌那样满口打包票？**
这恰恰与第四节审计的**节点地区结构**高度吻合：
- 首先，**香港节点天生处于 OpenAI、Claude 与 Google Gemini 的官方不支持地区名单中**（除非机场在服务端配置了精准的 DNS/SNI 分流把 AI 流量二次转发到美新日，否则直连香港落地必弹 `Unsupported Country/Region`）。
- 其次，在亚太低延迟节点里，**新加坡和日本、台湾**往往是解锁 Gemini 与 Claude 的主力跳板；但二猫云不仅在正文中自称“少了新加坡这一站”，而且其美国节点在 `2026-10-19` 历史表中的下载速率仅为 `17 Mbps`（134ms），日本节点若遇到多人共用同一出口 IP（尤其在“不限设备连接”策略下），极易触发 Anthropic 严苛的 Cloudflare 盾与风控封禁。
- 因此，二猫云未对 Claude 和 Gemini 做过度承诺，反而是符合其节点客观局限的提示。如果您平时重度使用 Claude 写代码或使用 Gemini Advanced，请提前阅读 [Claude 地区限制与 IP 风控排查](/ai-streaming/claude/) 及 [Gemini 区域解锁与分流规则配置](/ai-streaming/gemini/)。

### 3. 本地实测二猫云节点归属地与 AI/流媒体连通性命令

购入 ¥20 白猫套餐并连接节点后（假设本地代理混合端口为 `127.0.0.1:7897`；若使用二猫云定制客户端，请查看其设置页显示的本地 HTTP 代理端口号并替换 `7897`），可在 Windows PowerShell 中运行以下无偏见诊断脚本，10 秒内查清“到底有没有新加坡节点”以及“Claude/Gemini 能否打通”：

```powershell
# 1. 切换至某节点后，查询当前真实出口 IP、所在国家代码（loc）及数据中心归属（org/asn）
curl.exe -x http://127.0.0.1:7897 -s https://www.cloudflare.com/cdn-cgi/trace | Select-String -Pattern "ip=|loc=|colo=|warp="

# 2. 测量真实海外 HTTPS 链路的 TCP 握手、TLS 握手与首字节响应耗时（排查晚高峰卡顿）
curl.exe -x http://127.0.0.1:7897 -o NUL -s -w "DNS:%{time_namelookup}s | TCP:%{time_connect}s | TLS:%{time_appconnect}s | TTFB:%{time_starttransfer}s | Total:%{time_total}s`n" https://www.youtube.com/generate_204

# 3. 批量探测 ChatGPT、Claude、Gemini 与 Netflix 自制剧页面的 HTTP 状态码
foreach ($url in @("https://chatgpt.com/", "https://claude.ai/", "https://gemini.google.com/", "https://www.netflix.com/title/80018499")) {
  $code = curl.exe -x http://127.0.0.1:7897 -s -o NUL -w "%{http_code}" -m 8 $url
  Write-Output "$url -> HTTP $code"
}
```

如果第 2 步中发现所有节点均返回 `000`（连接超时），请先排查本地系统时间偏差（VLESS+TLS 对时间同步要求极严）或 TUN 虚拟网卡冲突，详见 [节点全部超时排查手册](/troubleshooting/all-nodes-timeout-check/) 与 [系统时间同步与 TLS 握手修复](/guides/system-time-tls-fix/)。
