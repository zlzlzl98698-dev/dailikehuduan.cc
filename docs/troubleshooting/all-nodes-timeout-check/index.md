faq:
  - q: 为什么昨天还好好的，今天一开机所有机场节点突然全部超时（-1ms）？
    a: 分布在不同地区机房的代理节点极少在同一秒同时物理损毁。全节点瞬间同时失效，九成以上触发了所有节点共用的前置公共环节：本地系统时间偏差超过 90 秒导致协议鉴权拒连、套餐到期或高倍率流量耗尽、开着失效旧代理导致订阅无法更新，或者所处网络切换后触发了防火墙、杀毒软件或校园网协议拦截。
  - q: 如何用 10 秒钟区分是自己电脑的问题，还是机场服务商上游崩了？
    a: 最快的方法是做跨设备与跨网络交叉测试：断开电脑 Wi-Fi，改用手机 5G 移动数据，先关闭手机客户端代理并刷新一次订阅，再对几个不同地区节点执行真连接测试。如果手机 5G 秒连而电脑全超时，故障 100% 在电脑本地或家庭路由器；如果手机 5G 刷新最新订阅后依然全员超时且官网失联，才高度指向服务端上游波动。
  - q: 为什么切换到新机场或更新订阅后，客户端内核里所有节点全部超时或直接不显示？
    a: 很多服务商已将主力节点升级为 AnyTLS、VLESS-Reality 或 Hysteria 2 等新协议。如果你仍在使用早已停止维护的 Clash for Windows、原版 Clash for Android 或多年未升级的旧内核，由于无法识别新协议字段，测速时会直接报错、跳过节点或全部显示超时。应迁移至活跃维护的 Clash Verge Rev、FlClash、v2rayN 或 Hiddify 最新版本。
  - q: 为什么 TCPing 测试显示 40ms 绿色正常，但 URLTest 真连接测试全是 -1ms 超时？
    a: TCPing 只验证本机到国内中转入口服务器的 TCP 三次握手是否畅通，不校验加密协议密钥、时间窗口、套餐流量和海外落地出口。只要时间偏差超标、套餐到期被后端踢出白名单，或中转服务器到海外落地机房断联，就会出现 TCPing 延迟很低但真连接全部 -1ms 的假通现象。
  - q: 在学校或公司 Wi-Fi 下突然全节点超时，但回宿舍或用手机热点就秒连是什么原因？
    a: 校园网与政企办公网经常部署深度包检测或端口策略，常见两种阻断：一是校园网 802.1X 网页认证掉线，所有外网流量被强行劫持到登录门户；二是对非 53 端口的高频 UDP 流量（如 Hysteria 2、TUIC）执行严厉限速或直接封禁。此时应先重新登录校园网认证页，再优先选用基于 TCP 443 端口的节点。
  - q: 所有节点都超时了，还能开着代理点“更新订阅”吗？
    a: 绝对不要开着失效代理更新订阅。如果客户端当前开启了系统代理或 TUN 模式，订阅更新请求自身也会被送进已经超时瘫痪的代理隧道里，最终导致订阅更新同步失败、形成死循环。正确做法是先彻底关闭系统代理与 TUN 开关，在本地直连网络下更新订阅。

# 所有机场节点突然全部超时怎么办？6 步快速定位客户端与服务端

<div class="answer-first-box">
  <div class="answer-first-label">核心结论（Answer-First）</div>
  <p>当你打开代理客户端发现<strong>“香港、日本、美国等所有机场节点突然全部超时 / 真连接全报 <code>-1ms</code>”</strong>时，不要急着卸载软件或认为服务商瞬间跑路。分布式节点极少在同一秒同时物理损坏，全军覆没几乎必定卡在所有节点共用的公共前置条件。按<strong>“先做手机 5G 交叉验证 → 再按 6 层排查树依次核验本地时钟、账户到期与倍率、内核协议兼容（如 AnyTLS / VLESS-Reality）、防火墙与杀软拦截、校园网 UDP/IPv6 阻断、上游入口切换”</strong>的顺序操作，配合 PowerShell <code>Test-NetConnection</code> 与 <code>curl -I --proxy</code> 实测，通常 5 分钟内即可精准锁定病灶在客户端还是服务端。</p>
</div>

## 一、症状判断表：5 类“全节点超时”特征快速分流

在动手改任何配置前，先花 30 秒观察客户端界面的报错模式与网络环境特征。不同维度的症状组合，已经直接指明了故障最可能藏在哪一层：

| 观察到的症状特征 | 常见日志关键词 / 伴随现象 | 优先排查层级 |
|---|---|---|
| 所有地区节点 1 秒内全部报 `-1ms` 或 `timeout`，同一 Wi-Fi 下手机端却正常 | `bad timestamp`、`x509: certificate`、`tls: bad record MAC` | **L1 本地系统时钟偏差**（先对表手机看分钟/年份/时区） |
| 节点列表正常但全线连不上，近期刚高强度看过视频或下载大文件 | `EOF`、`connection reset by peer`、`invalid user` | **L2 套餐到期、流量耗尽或高倍率扣光** |
| 更新订阅后突然全红，或部分新协议节点测速无反应/报未知类型 | `unsupported protocol`、`unknown type: anytls`、`vless reality` 报错 | **L3 客户端内核版本过旧**（如仍用停更客户端） |
| 电脑完全无任何出站流量，或安装国产安全软件后突然全断 | 核心进程被拦截、本地 `127.0.0.1:7897` 无法建立连接 | **L4 本地防火墙、杀软 HTTPS 扫描或残留代理冲突** |
| 在家正常，到学校宿舍/公司/酒店 Wi-Fi 后全超时；或仅 Hysteria 2 全红 | 重定向到校园网认证页、仅 UDP 协议超时而 TCP 443 存活 | **L5 校园网认证掉线、UDP 阻断或残缺 IPv6** |
| 校准时间 + 关闭代理直连刷新订阅报错，且手机切 5G 蜂窝网络依然全超时 | 订阅返回 404/502/超时，官网面板无法登录且官方通知群异常 | **L6 上游中转入口切换、全站波动或停服** |

**10 秒分界线测试（强烈建议第一步执行）**：拿出手机，**关闭 Wi-Fi 切换到 5G 移动数据**，暂时关掉手机代理开关，刷新一次订阅后再开代理测试两个不同地区节点。
- 如果**手机 5G 正常秒连**：说明机场服务端和你的套餐大概率完好无损，100% 是电脑本地环境、杀毒软件、时钟或家里路由器出了问题。
- 如果**手机 5G 同样全节点超时**：则说明问题集中在你的账户配额/Token 失效，或者服务商上游中转线路正在发生全站维护或故障。

## 二、原因分类：全节点同时超时的 6 层排查树

定位全节点超时必须遵循“从本地到远端、从低成本到高排查成本”的树状排除法，避免在错误的方向反复折腾：

### L1 层：本地系统时钟偏差超过 ±90 秒

这是“昨天还好好的、今天电脑所有节点瞬间全红”的头号隐形原因。现代主流加密代理协议对客户端和服务端 UTC 时间戳一致性有硬性安全校验：
- **VMess（AEAD）** 与 **VLESS-Reality** 均要求双方系统时间误差控制在 **±90 秒** 以内（部分环境宽容至 120 秒）。
- **Trojan / TLS** 以及 HTTPS 订阅更新则依赖数字证书 `NotBefore` 与 `NotAfter` 有效期。

只要遇到 Windows 与 Linux 双系统切换导致相差 8 小时、主板 CMOS 电池亏电导致年份回退、或者虚拟机休眠唤醒后时钟停滞，服务端就会直接静默丢包，表现为所有节点全超时。详细原理与各系统命令修复见 [系统时间偏差导致 TLS 握手与节点全部超时修复指南](/guides/system-time-tls-fix/)。

### L2 层：套餐到期、流量耗尽与高倍率节点暗扣

很多用户习惯在客户端开启“自动选择（url-test）”策略组，却没有留意自己究竟连上了哪条线路。部分服务商的特殊解锁节点、专线节点带有 `2x`、`3x`、`5x` 甚至更高的结算倍率（倍率扣费逻辑参见 [机场流量倍率计算机制](/routes/multipliers/)）。如果前一晚下载大型文件、触发了系统自动更新或网盘后台同步，当月配额可能在几小时内被高倍率节点瞬间吃光。

一旦账户到达到期时间或剩余流量归零，机场后端控制面板会在 1 至 3 分钟内把你的认证凭证从所有节点的鉴权白名单中踢出，导致节点列表看似还在，实则全军覆没。此外，短时间内多线程 BT 下载或超出套餐设备数上限，也可能触发后端 10 至 30 分钟的临时风控封禁。

### L3 层：客户端内核过旧，不兼容 AnyTLS / VLESS-Reality 等新协议

代理生态正在快速向 **VLESS-Reality**、**Hysteria 2**、**TUIC** 以及较新的 **AnyTLS** 协议迁移。如果你电脑上还装着用了几年的旧版工具（例如早已归档停止维护的 Clash for Windows、Clash for Android，或者未升级核心的老版 v2rayN / Clash Meta），一旦服务商在后台把旧节点批量替换为 AnyTLS 或新版 Reality 参数，旧客户端在解析订阅时会发生静默丢弃、协议字段识别失败或握手参数错误，直接表现为全部节点 `timeout` 或订阅里节点变空。

请对照本站客户端指南核对当前版本是否属于活跃维护的现代客户端与内核：[Clash Verge Rev](/clients/clash-verge-rev/)、[FlClash](/clients/flclash/)、[v2rayN](/clients/v2rayn/)、[Hiddify](/clients/hiddify/)，以及底层核心 [Mihomo](/clients/mihomo/) 和 [sing-box](/clients/sing-box/)。

### L4 层：Windows 防火墙、杀毒软件 HTTPS 扫描与残留代理拦截

在电脑端，安全软件和系统网络栈拦截同样会导致“全节点同时断流”：
1. **杀毒软件拦截或流量扫描**：部分国内安全卫士或第三方杀软（如自带“HTTPS 流量扫描/网页防护”的套件）会主动阻断 `verge-mihomo.exe`、`mihomo.exe`、`xray.exe` 或 `sing-box.exe` 对外发起的加密连接，或者直接把核心程序隔离，导致界面能打开但底层内核根本没有出站网络权限。
2. **开着旧代理死循环更新订阅**：节点全部超时后，用户点“更新订阅”试图拉取新入口，但系统代理或 TUN 依然开着，结果订阅请求自身也被丢进死掉的代理通道里超时失败。
3. **双虚拟网卡抢路由**：之前开启的网游加速器、公司内网 VPN（如 EasyConnect、GlobalProtect）或 Tailscale 抢占了默认路由表，可延伸对照 [TUN 与系统代理冲突排查](/troubleshooting/tun/)。

### L5 层：校园网/企业网 UDP 阻断、802.1X 掉线与残缺 IPv6

当你离开家庭宽带，在学校宿舍、图书馆、公司内网或酒店 Wi-Fi 下突然出现全节点超时，高频触发点有三类：
- **校园网 / 公共 Wi-Fi 认证失效**：浏览器看似连接了 Wi-Fi，其实尚未完成网页认证（Captive Portal），所有出站 TCP/UDP 请求全被网关劫持或静默丢弃。
- **UDP 高端口 QoS 限速或封禁**：校园网与政企防火墙常对非 53/123 端口的 UDP 数据包直接封杀，导致 Hysteria 2、TUIC 等基于 QUIC/UDP 的节点集体超时。
- **本地残缺 IPv6 抢先握手**：路由器下发了无效或国际出口断流的 IPv6 前缀，而节点中转域名同时解析出 AAAA 和 A 记录时，客户端优先尝试 IPv6 建连并卡死在超时阶段。

### L6 层：上游中转入口批量切换、全站波动与停服核验

国内中转节点遭遇骨干网波动、端口被运营商阶段性阻断或入口机器遭受 DDoS 攻击时，服务商会在后台紧急更换一批新的中转入口域名或端口，并通知用户刷新订阅。此时旧订阅里的所有中转地址确实会全部失联；只有在极少数情况下，才会遇到服务商长期跑路或停止运维。

## 三、逐项检查与修复操作：按 6 步顺序推进

请严格按照以下 1 到 6 步的顺序执行排查和修复，每完成一步就观察状态变化，命中即止：

### 第 1 步：关闭所有代理开关，确认本地裸网与认证页正常

先在客户端界面同时关闭**「系统代理（System Proxy）」**和**「TUN 模式（TUN Mode）」**，并临时退出其它正在运行的网游加速器或公司 VPN。然后打开浏览器访问一个非缓存国内网页（如 `https://www.baidu.com` 或学校认证网关），确认没有弹出校园网/酒店登录认证页，且本地物理网络处于正常直连状态。

### 第 2 步：比对并强制同步系统 UTC 时间

打开终端核对本地时间与时区（Windows 用户可执行以下命令检查）：

```powershell
# 查看当前日期、时区以及与阿里云 NTP 的偏差秒数
Get-Date
tzutil /g
w32tm /stripchart /computer:ntp.aliyun.com /samples:3 /dataonly
```

若时区不是 `China Standard Time` 或偏差大于 `1.0s`，使用管理员 PowerShell 强制同步：

```powershell
Set-Service -Name w32time -StartupType Automatic
Start-Service -Name w32time
w32tm /config /manualpeerlist:"ntp.aliyun.com,0x8 ntp.tencent.com,0x8" /syncfromflags:manual /reliable:YES /update
w32tm /resync /force
```

同步完成后务必在客户端点击一次「重启内核」。双系统用户或 macOS/Linux 用户请直接对照 [系统时间偏差修复指南](/guides/system-time-tls-fix/) 根治。

### 第 3 步：直连刷新订阅，核验账户到期日与剩余流量

保持第 1 步中的**关闭代理直连状态**，回到客户端「订阅（Profiles）」页面点击刷新订阅：
- **查看流量与到期提示**：核对订阅卡片下方解析出的已用流量 / 总流量和到期时间。如果显示已用尽或已过期，登录服务商官网控制台确认状态（续费或重置流量后需等待 2 至 5 分钟后端同步，再刷新订阅）。
- **如果刷新订阅直接报错或超时**：说明服务商旧的订阅域名可能被墙或更换，可查阅 [订阅更新报错排查](/troubleshooting/subscription/) 并尝试关闭代理登录官网后台获取最新订阅链接。

### 第 4 步：核对内核版本与系统防火墙放行规则

1. **升级客户端与内核**：在 Clash Verge Rev「设置 → Clash 设置 → Clash 内核」或 v2rayN「检查更新」中，确认底层正在运行最新稳定版或 Release 版的 **Mihomo / sing-box / Xray-core**，确保完整支持 `AnyTLS`、`VLESS-Reality` 与 `Hysteria 2`。若仍在使用已停更的 Clash for Windows，请先彻底卸载并迁移到现代客户端。
2. **放行 Windows 防火墙与排查杀软**：打开「Windows 安全中心 → 防火墙和网络保护 → 允许应用通过防火墙」，确认 `Clash Verge`、`verge-mihomo.exe`（或对应客户端主程序及内核）在专用和公用网络均已勾选放行；若装有第三方杀毒软件，先临时关闭其“HTTPS 保护/流量扫描”测试是否立即恢复。

### 第 5 步：测试 TCP 443 端口节点并临时关闭 IPv6

1. **绕开 UDP 阻断**：在节点列表中专门挑选标注为 `VLESS`、`Trojan` 或端口为 `443` 的 TCP 节点进行单点测试，不要只测 `Hysteria 2`、`TUIC` 或“自动选择”组，观察是否恢复。
2. **关闭客户端 IPv6**：在客户端设置（或全局 Merge 配置）中将 `ipv6` 设为 `false`，同时把 DNS 策略或路由出站设为优先 IPv4，排查是否因残缺 IPv6 导致全线握手卡死。

### 第 6 步：切换手机 5G 热点与确认上游全站状态

如果上述 5 步走完电脑端依然全超时，请将电脑直接连接手机开启的 **5G 个人热点** 再次测试：
- 若连上手机热点立刻全部恢复正常，说明故障根源在你的**家庭光猫/路由器或当前所在宽带运营商阻断**（如路由器 DNS 劫持或地区宽带抽风，可重启光猫路由器并参考 [DNS 排查指南](/troubleshooting/dns/)）。
- 若手机 5G 热点下且使用最新客户端、最新订阅依然全部节点超时，则问题已锁定在**服务端上游**。

## 四、验证结果：PowerShell `Test-NetConnection` 与 `curl -I --proxy` 实测步骤

排障完成后，不要只看客户端界面上“圆点变绿了没”，建议用 Windows PowerShell 原生命令做一次两层实测，精准区分“物理端口通不通”与“代理隧道通不通”。

### 第 1 步：使用 `Test-NetConnection` 检测中转服务器 TCP 端口可达性

从你的客户端节点详情中任选一个主力节点，记录下它的服务器地址（域名或 IP）与端口号（例如 `443` 或中转端口），先在**关闭代理**的状态下于 PowerShell 运行：

```powershell
# 将 <中转域名或IP> 和 <节点端口> 替换为节点配置里的真实参数
Test-NetConnection -ComputerName <中转域名或IP> -Port <节点端口>
```

**结果判读**：
- **`TcpTestSucceeded : True`**：说明你当前网络到该节点中转入口的 TCP 链路完全畅通，端口没有被本地防火墙或运营商拦截。如果此时客户端依然真连接 `-1ms`，问题一定出在**协议鉴权（时钟/密码/套餐到期）、内核不兼容（如 AnyTLS/Reality 字段）或中转机到海外落地机的后端断联**。
- **`TcpTestSucceeded : False`**：说明三层/四层 TCP 握手根本没能到达目标端口。如果是本地全部地址都 `False`，优先检查本机防火墙、杀软拦截或是否连错断网 Wi-Fi；如果只有该机场节点 IP 全 `False` 而访问国内网站正常，说明该批次中转入口 IP/端口已被屏蔽或下线，需直连更新订阅获取新入口。

### 第 2 步：使用 `curl -I --proxy` 验证真实端到端代理返回码

开启客户端的系统代理（以 Clash Verge Rev 默认混合端口 `7897` 为例，v2rayN 默认通常为 `10808`/`10809`，请以软件界面底部显示端口为准），在 PowerShell 运行：

```powershell
# 测试通过本地代理端口请求 Cloudflare 204 探测端点
curl.exe -I --connect-timeout 8 --proxy http://127.0.0.1:7897 https://cp.cloudflare.com/generate_204
```

**预期成功输出**：终端应首先显示 `HTTP/1.1 200 Connection established`（表明本机已成功与本地代理端口建立 CONNECT 隧道），紧接着返回 `HTTP/2 204`（或 `HTTP/1.1 204 No Content`）。看到 `204` 状态码即证明从本机客户端、协议加密握手到海外落地出口已全链路恢复。

## 五、下一步处置：如果 6 步全通依然无法恢复怎么办

当你严格走完以上 6 步并完成命令行探测后，按不同终点状态采取对应后续行动：

- **情况 A（订阅能拉取但节点空了，或特定地区/特定协议才断）**：请对照 [节点连接超时深度排查树](/troubleshooting/timeout/) 与 [连接上节点却无法打开网页排查](/troubleshooting/disconnected/)，进一步检查客户端规则模式（是否误设为 `Direct` 直连或 `Global` 下选中了 `REJECT`）以及本地 DNS 污染设置。
- **情况 B（手机 5G 与电脑同时全超时，官网失联且官方渠道长期无公告）**：切勿轻信搜索引擎广告里的来路不明破解工具或弹窗推广链接。建议先按 [机场停服与跑路核验指南](/safety/closures/) 交叉核对服务商主域名、工单/通知渠道存活状态、历史公告记录与账单凭证，确认是否属于临时维护波动或已经进入停服状态后再做下一步决策。

## 六、常见问题（FAQ）

### 为什么昨天还好好的，今天一开机所有机场节点突然全部超时（-1ms）？

分布在不同地区机房的代理节点极少在同一秒同时物理损毁。全节点瞬间同时失效，九成以上触发了所有节点共用的前置公共环节：本地系统时间偏差超过 90 秒导致协议鉴权拒连、套餐到期或高倍率流量耗尽、开着失效旧代理导致订阅无法更新，或者所处网络切换后触发了防火墙、杀毒软件或校园网协议拦截。

### 如何用 10 秒钟区分是自己电脑的问题，还是机场服务商上游崩了？

最快的方法是做跨设备与跨网络交叉测试：断开电脑 Wi-Fi，改用手机 5G 移动数据，先关闭手机客户端代理并刷新一次订阅，再对几个不同地区节点执行真连接测试。如果手机 5G 秒连而电脑全超时，故障 100% 在电脑本地或家庭路由器；如果手机 5G 刷新最新订阅后依然全员超时且官网失联，才高度指向服务端上游波动。

### 为什么切换到新机场或更新订阅后，客户端内核里所有节点全部超时或直接不显示？

很多服务商已将主力节点升级为 AnyTLS、VLESS-Reality 或 Hysteria 2 等新协议。如果你仍在使用早已停止维护的 Clash for Windows、原版 Clash for Android 或多年未升级的旧内核，由于无法识别新协议字段，测速时会直接报错、跳过节点或全部显示超时。应迁移至活跃维护的 Clash Verge Rev、FlClash、v2rayN 或 Hiddify 最新版本。

### 为什么 TCPing 测试显示 40ms 绿色正常，但 URLTest 真连接测试全是 -1ms 超时？

TCPing 只验证本机到国内中转入口服务器的 TCP 三次握手是否畅通，不校验加密协议密钥、时间窗口、套餐流量和海外落地出口。只要时间偏差超标、套餐到期被后端踢出白名单，或中转服务器到海外落地机房断联，就会出现 TCPing 延迟很低但真连接全部 -1ms 的假通现象。

### 在学校或公司 Wi-Fi 下突然全节点超时，但回宿舍或用手机热点就秒连是什么原因？

校园网与政企办公网经常部署深度包检测或端口策略，常见两种阻断：一是校园网 802.1X 网页认证掉线，所有外网流量被强行劫持到登录门户；二是对非 53 端口的高频 UDP 流量（如 Hysteria 2、TUIC）执行严厉限速或直接封禁。此时应先重新登录校园网认证页，再优先选用基于 TCP 443 端口的节点。

### 所有节点都超时了，还能开着代理点“更新订阅”吗？

绝对不要开着失效代理更新订阅。如果客户端当前开启了系统代理或 TUN 模式，订阅更新请求自身也会被送进已经超时瘫痪的代理隧道里，最终导致订阅更新同步失败、形成死循环。正确做法是先彻底关闭系统代理与 TUN 开关，在本地直连网络下更新订阅。
